# 문서 작성 규칙

ProgInOne 저장소의 모든 문서가 따르는 작성 규칙입니다.
Google의 문서화 가이드를 기반으로 하고, 한국어 문서에 맞게 일부 조정했습니다.

## 근거가 되는 가이드

- [Google Documentation Best Practices][best-practices]
- [Google Markdown Style Guide][md-style]
- [Design Docs at Google][design-docs]
- [Google Developer Documentation Style Guide][dev-style] (용어·어조 참고)

## 핵심 원칙

1.  **최소 유효 문서(Minimum viable documentation).**
    적지만 정확하고 최신인 문서가 많고 낡은 문서보다 낫습니다.
    아직 필요하지 않은 문서는 빈 파일로 만들지 않고 [문서 지도](/docs/README.md)에 "예정"으로만 표시합니다.
2.  **코드와 문서를 같은 변경에서 수정합니다.**
    동작·API·스키마·설정을 바꾸는 PR은 관련 문서도 함께 수정해야 합니다.
    리뷰어는 문서 갱신 누락을 결함으로 취급합니다.
3.  **죽은 문서는 삭제합니다.**
    틀린 문서는 없는 문서보다 해롭습니다. 삭제된 내용은 git 이력에서 복구할 수 있습니다.
4.  **완벽보다 개선(Better is better than best).**
    합리적인 개선은 빠르게 반영하고, 큰 수정은 별도 변경으로 나눕니다.
5.  **중복을 피하고 링크합니다.**
    외부 도구 사용법(예: Vite, Drizzle)은 공식 문서에 링크하고, 우리 프로젝트에 특화된 내용만 씁니다.
    같은 사실은 한 곳에만 쓰고 나머지는 링크합니다. 용어 정의는 [용어집](/docs/glossary.md)이 유일한 원천입니다.

## 문서 유형과 위치

| 유형 | 위치 | 목적 | 수명 |
|---|---|---|---|
| 루트 README | `/README.md` | 프로젝트 소개, 빠른 시작, 문서 진입점 | 상시 최신 유지 |
| 패키지 README | `/apps/*/README.md`, `/packages/*/README.md` | 디렉터리의 목적, 먼저 읽을 파일, 공개 API | 상시 최신 유지 |
| 문서 지도 | `/docs/README.md` | 모든 문서의 목록과 읽는 순서 | 상시 최신 유지 |
| 용어집 | `/docs/glossary.md` | 공통 용어 정의 | 상시 최신 유지 |
| 결정 기록 | `/docs/decisions.md` | 합의된 결정과 근거 | 추가만 함 (항목 삭제 금지) |
| PRD | `/docs/product/` | 무엇을, 왜 만드는가 | 구현 후 결정 기록으로 동결 |
| 설계 문서 | `/docs/design/` | 어떻게 만드는가, 대안과 트레이드오프 | 구현 후 결정 기록으로 동결 |
| 개발 가이드 | `/docs/guides/` | 시작하기, 테스트, 디버깅, 릴리스 | 상시 최신 유지 |
| 변경 이력 | `/CHANGELOG.md` | 릴리스별 변경 사항 | 릴리스마다 추가 |
| 기여 가이드 | `/CONTRIBUTING.md` | 브랜치, 커밋, 리뷰, 완료 기준 | 상시 최신 유지 |

**설계 문서의 수명 규칙** (Google 방식):
설계 문서는 구현 전에 피드백을 모으는 도구입니다.
구현이 끝나면 "현재 동작 설명서"가 아니라 "결정의 기록"이 됩니다.
구현 중 계획이 바뀌면 문서를 갱신하고, 구현 이후 큰 변경은 새 설계 문서(개정 문서)를 쓰고 원문에서 링크합니다.
현재 동작은 코드, 패키지 README, 개발 가이드가 설명합니다.

## 설계 문서 템플릿

`/docs/design/` 아래 모든 설계 문서는 아래 구조를 따릅니다.
분량은 문서당 대략 A4 10~20쪽 이내를 목표로 하고, 그보다 커지면 하위 문제로 나눕니다.

```markdown
# <시스템 이름> 설계

<한두 문장 요약: 이 문서가 무엇을 설계하는지>

- 상태: 초안 | 검토 중 | 승인됨 | 구현됨 | 대체됨
- 작성: <작성자>
- 최종 수정: YYYY-MM-DD
- 관련 문서: <링크>

## 배경과 범위          (Context and scope)
## 목표와 비목표        (Goals and non-goals)
## 설계                 (The actual design)
### 개요
### 상세 ...
## 검토한 대안           (Alternatives considered)
## 교차 관심사           (Cross-cutting concerns: 보안, 개인정보, 관측성, 성능, 접근성, 테스트)
## 미결 사항             (Open questions)
## 참고 자료             (See also)
```

- **비목표**는 목표를 뒤집은 문장이 아니라 "합리적으로 목표가 될 수 있었지만 의도적으로 제외한 것"입니다.
- **검토한 대안**은 가장 중요한 섹션 중 하나입니다. 대안마다 장단점과 채택하지 않은 이유를 씁니다.
- **API·스키마**는 설계 판단에 필요한 만큼만 스케치합니다. 정식 정의는 코드(zod 스키마, Drizzle 스키마)가 원천입니다.
- 코드나 의사코드는 꼭 필요한 곳에만 씁니다.

## Markdown 규칙

Google Markdown Style Guide를 따르며, 아래 사항을 명시합니다.

- 파일당 H1은 하나이며 문서 제목입니다. H1 바로 다음에 1~3문장 소개를 씁니다.
- 제목은 ATX 방식(`#`)을 쓰고, 앵커가 겹치지 않도록 고유하고 구체적으로 씁니다.
  예: `## 요약` 대신 `## 숙련도 계산 요약`.
- 코드 블록은 항상 펜스(```)를 쓰고 언어를 지정합니다. 언어가 없으면 `text`.
- 링크 텍스트는 내용을 설명해야 합니다. "여기", "링크" 같은 텍스트는 쓰지 않습니다.
- 저장소 내 문서 링크는 같은 디렉터리면 상대 경로, 아니면 루트 기준 절대 경로(`/docs/...`)를 씁니다.
- 긴 URL이나 반복되는 URL은 참조 링크로 쓰고, 처음 쓰인 섹션 끝에 정의합니다.
- 표는 여러 항목을 두 축으로 훑어볼 때만 씁니다. 긴 설명은 목록으로 씁니다.
- HTML 태그는 쓰지 않습니다.
- 다이어그램은 텍스트로 유지 가능한 Mermaid 또는 ASCII를 우선합니다. 이미지는 UI 화면처럼 텍스트로 설명하기 어려운 경우에만 쓰고 반드시 대체 텍스트를 붙입니다.
- 긴 목록이나 자주 바뀌는 목록은 번호를 모두 `1.`로 씁니다.

### Google 가이드와 다르게 적용하는 부분

| Google 규칙 | ProgInOne 적용 | 이유 |
|---|---|---|
| 80자 줄바꿈 | **문장 단위 줄바꿈** (한 문장 = 한 줄) | 한글은 전각 폭이라 80자 규칙이 어색함. 문장 단위가 diff 리뷰에 더 유리함 |
| `[TOC]` 지시자 | 쓰지 않음 | GitHub가 지원하지 않음. GitHub의 자동 목차(Outline)를 사용 |

## 언어와 어조

- 본문은 한국어로 쓰고 "~합니다"체를 씁니다.
- 기술 용어, 코드 식별자, API 이름은 영어를 그대로 씁니다. 처음 나올 때 필요하면 한국어 설명을 붙입니다.
- 용어는 [용어집](/docs/glossary.md)의 표기를 따릅니다. 새 용어는 용어집에 먼저 추가합니다.
- 주관적 수식어("매우 간단한", "강력한")보다 측정 가능한 표현을 씁니다. 예: "200ms 이내".
- 요구사항에는 RFC 2119 의미의 강도 표현을 씁니다: **반드시**(MUST), **해야 한다**(SHOULD), **할 수 있다**(MAY).

## 문서 리뷰 체크리스트

- [ ] H1 다음에 1~3문장 소개가 있는가
- [ ] 설계 문서라면 템플릿의 필수 섹션(배경, 목표/비목표, 설계, 대안, 교차 관심사)을 갖췄는가
- [ ] 용어가 용어집과 일치하는가
- [ ] 다른 문서와 같은 사실을 중복해서 쓰지 않고 링크했는가
- [ ] 코드 블록에 언어가 지정되었는가
- [ ] 링크가 깨지지 않았는가 (CI의 링크 검사 통과)
- [ ] 문서 지도(`/docs/README.md`)가 갱신되었는가
