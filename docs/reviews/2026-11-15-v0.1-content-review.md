# v0.1 콘텐츠 AI 교차 검토 기록 (2026-11-15)

v0.1 콘텐츠(레슨 4개, 문제 56개)를 독립 AI 검토자(`ai:reviewer`)가 전수 검토한 기록입니다.
검토 방법, 단원별 판단, 직접 고친 내용, 최종 문제 구성과 남은 한계를 적습니다.

- 상태: 완료
- 검토: 독립 AI 검토자 (`ai:reviewer`, [D-027](/docs/decisions.md))
- 검토일: 2026-11-15
- 관련 문서: [콘텐츠·문제 시스템 설계](/docs/design/content-and-exercises.md), [콘텐츠 작성 가이드](/docs/guides/content-authoring.md), [결정 기록](/docs/decisions.md)

## 검토 범위와 방법

대상은 아래 4개 단원의 레슨 본문과 문제 전부입니다.
모든 문제가 `review.status: draft`, `draftedBy: ai:claude`였습니다.

| 단원 | 중요도 | 목표 문제 수 |
|---|---|---|
| `css.box.model` 박스 모델 | standard (HTML/CSS 핵심) | 10 |
| `js-basics.start.first-program` 첫 프로그램 | standard | 12 |
| `js-basics.start.reading-errors` 오류 메시지 읽기 | standard | 12 |
| `js-basics.values.variables` 변수와 상수 ★ | core | 22 |

`variables`가 핵심 단원이고 전체 수가 적어서, 샘플링 없이 **전수 검토**했습니다.

검토 절차:

1. 초안 작성 대화를 보지 않고, 원본 파일과 설계 문서·작성 가이드·결정 기록(D-026~D-028)만 읽었습니다.
1. 검토 시작 전에 `pnpm content:check`와 `pnpm content:check:run`을 직접 실행해 오류 0개를 확인했습니다.
1. 레슨마다 [품질 체크리스트](/docs/design/content-and-exercises.md#품질-체크리스트-검토자용)의 레슨 항목, 표준 섹션 구성, 개념 중요도별 깊이, 선수 개념 순서, 엄격 모드(D-026)와의 일관성을 확인했습니다.
1. 문제마다 체크리스트의 문제 항목을 확인했습니다. 특히 다음을 봤습니다.
   - 정답이 하나로 확정되는지, 체크가 맞는 프로그램을 모두 받아들이는지
   - 오답 선택지와 `misconception` 연결이 실제 오개념과 맞는지
   - 힌트 3단계가 정답 전체를 주지 않는지
   - 난이도가 루브릭과 맞는지
1. 오류 메시지가 나오는 예제와 문제는 Node(V8)와 저장소의 러너(`packages/runner`의 실행 전 문법 검사)로 실제 메시지와 위치를 확인했습니다.
1. `pnpm content:build`로 빌드하고 앱(`PROGINONE_PORT=4415`)을 띄워 레슨 4개를 Playwright로 캡처해 렌더링을 확인했습니다.
   예제의 실행 결과도 앱에서 직접 확인했습니다.
1. 수정 뒤 `pnpm content:check`(오류 0, 경고 0)와 `pnpm content:check:run`(문제 56개, 예제 14개, 실패 0)을 다시 실행했습니다.

### 검토자가 직접 쓴 문제의 2차 검토

유형을 바꾸거나 새로 쓴 7문제(아래 [구현 문제 전환](#구현-문제-전환과-추가))는 검토자 자신이 쓴 문제입니다.
자기 승인을 피하기 위해, **분리된 컨텍스트의 2차 AI 검토자**에게 이 7문제만 다시 검토하게 했습니다.
2차 검토는 7문제 중 3개를 그대로 승인하고 4개에 수정을 요청했습니다.
요청 내용은 모두 반영한 뒤 승인했습니다.

- `impl-laundry-order`: "빨래 널기"와 "빨래 넣기"가 한 글자 차이라 숨김 체크에서 원인을 알기 어려움 → "빨래 말리기"로 변경, 난이도 3 → 2
- `impl-error-report`: 숨김 체크 하나로는 어느 줄이 틀렸는지 알 수 없음 → 종류·설명·줄 번호를 각각 검사하는 체크로 분리
- `impl-swap-values`: 난이도 4 → 3(루브릭 합 6), 글자를 다시 쓰는 풀이에 대한 해설 추가
- `impl-price-quantity`: 채점할 수 없는 `const` 강제 문구를 "골라 만들어 보세요"로 완화, 힌트 3 축소
- `impl-print-goal`·`impl-declare-nickname`: 해설 문장 정정(아직 배우지 않았다는 잘못된 안내 삭제 등)

`draftedBy`는 스키마 형식(`ai:<제공자>`)에 따라 `ai:claude`로 두었습니다.
이 7문제를 검토자가 썼다는 사실은 이 기록과 git 이력에 남습니다.

### js-basics.start.reading-errors

레슨과 문제 12개를 승인했습니다.

- **러너의 실제 메시지와 맞지 않는 설명을 고쳤습니다.**
  ProgInOne은 실행 전에 acorn으로 문법을 검사하므로, `SyntaxError`의 설명이 Chrome과 다릅니다.
  예: `missing ) after argument list` → `Unexpected token`, `Invalid or unexpected token` → `Unterminated string constant`.
  표시 형식도 `Uncaught ... at main.js:3:1`이 아니라 `ReferenceError: ... (3번째 줄)`입니다.
  - 레슨에 ProgInOne 콘솔의 형식을 추가하고, "브라우저 문장이 그대로 나온다"던 안내를 "실행 중 오류는 브라우저 문장, `SyntaxError`는 ProgInOne의 문법 검사 문장"으로 고쳤습니다.
  - 예제 해설의 콘솔 출력을 앱에서 실제로 보이는 모양으로 바꿨습니다.
  - 버그 수정 문제의 오류 메시지를 학습자가 실행하면 보게 될 형식으로 바꿨습니다(`fix-name-typo`, `fix-missing-quotes`).
  - Chrome 형식의 메시지를 읽는 문제에는 "Chrome 개발자 도구에서"라고 출처를 밝혔습니다.
- 레슨: `SyntaxError`의 흔한 원인 "문장 사이 세미콜론 빠뜨림"은 줄 끝에서는 대개 성립하지 않습니다(자동 세미콜론 삽입). "한 줄에 쓴 두 문장 사이"로 고쳤습니다.
- 레슨·문제: 세 번째 예제(`(`로 시작하는 다음 줄)의 해설에 "줄 끝 세미콜론은 보통 자동으로 보충되지만, 다음 줄이 `(`로 시작하면 이어 붙여 읽는다"를 추가했습니다. 원래 해설은 세미콜론이 없으면 줄이 항상 이어진다고 읽힐 수 있었습니다(`mcq-cause-on-previous-line`도 같이 수정).
- 레슨: 설명 없이 쓰인 "함수"에 짧은 정의를 붙였습니다.
- 오개념 연결 오류 2건을 고쳤습니다.
  - `fill-error-unclosed-quote`: 오답 `ReferenceError`에 "오타는 모두 SyntaxError" 오개념이 붙어 있었습니다(반대 방향이라 삭제).
  - `mcq-syntax-error-runs-nothing`: 같은 이유로 선택지 d의 오개념을 삭제했습니다.
- 개념 확인(선택형)이 5개(42%)로 목표 범위를 넘었습니다. 가장 단순한 `mcq-syntax-error-meaning`(L1)을 없애고, 오류 메시지의 세 부분을 찾아 출력하는 프로그램 문제 `impl-error-report`를 넣었습니다. 같은 내용은 `mcq-syntax-error-runs-nothing`과 레슨이 다룹니다.

### js-basics.values.variables ★

레슨과 문제 22개를 승인했습니다.
핵심 개념 기준(원리 2관점, 값 추적 표, 예제 5개 중 예측 3개, 오개념 12개 모두 흔한 실수에 포함, 확인 문제 4개)을 충족합니다.
레슨이 엄격 모드(D-026)를 이미 반영하고 있었습니다(`let` 없는 대입 → `ReferenceError`).

- `SyntaxError` 설명 불일치를 위와 같이 고쳤습니다. 레슨 본문, 흔한 실수, `fix-let-twice`, `fix-assign-direction`, `fix-hyphen-name`, `mcq-const-without-value`, 오개념 파일의 `reality`가 대상입니다.
  `fix-assign-direction`은 ProgInOne 메시지(`Assigning to rvalue`)와 Chrome 메시지(`Invalid left-hand side in assignment`)를 함께 보여 주고, 힌트에서 두 표현을 모두 풀이합니다.
- `mcq-let-purpose`: "콘솔에 90이 출력된다" 선택지의 오개념을 `js.mc.log-is-return`에서 `js.mc.expression-prints-itself`로 바꿨습니다.
- `mcq-let-without-value`: 힌트 3의 "레슨에서"가 어느 레슨인지 모호해 "\"첫 프로그램\" 단원에서"로 고쳤습니다.
- `mcq-const-prevents`: 힌트 3이 학습자가 모르는 컴포넌트 이름 `CompareTable`을 썼습니다. "let·const 비교표"로 고쳤습니다.
- 난이도 정정: `fill-choose-const-let` 3 → 2, `fix-hyphen-name` 4 → 3. 둘 다 루브릭 합계와 맞췄습니다.
- 구현 문제가 0개였고 코드 이해가 50%였습니다. 빈칸 3개와 예측 1개를 프로그램 작성 문제 4개로 바꿨습니다(아래 표).

## 구현 문제 전환과 추가

함수는 모듈 6에서 배우므로, `entry` 없는 프로그램 작성 문제(D-028)로 만들었습니다.
채점은 `console`(출력)과 `program`(끝난 뒤 변수 값, `noError`) 체크로만 합니다.
엄격 모드라서 `let` 없이 대입하거나 같은 이름으로 `let`을 다시 쓰면 실패합니다.

| 단원 | 없앤 문제 | 새 문제 | 주 개념 | 난이도 |
|---|---|---|---|---|
| first-program | `fill-print-goal` | `impl-print-goal`: 세 줄 출력 프로그램을 처음부터 작성 | console-log | 2 |
| first-program | `fill-semicolon-one-line` | `impl-laundry-order`: 조건을 읽고 실행 순서를 정해 출력 (숨김 체크) | statements | 2 |
| reading-errors | `mcq-syntax-error-meaning` | `impl-error-report`: 오류 메시지의 종류·설명·줄 번호를 찾아 출력 (숨김 체크 4개) | error-messages | 2 |
| variables | `predict-let-reassign` | `impl-change-lives`: 변수를 만들고 같은 변수의 값을 바꿔 출력 | let | 2 |
| variables | `fill-declare-nickname` | `impl-declare-nickname`: 변수를 만들고 그 변수로 출력 | let | 2 |
| variables | `fill-swap-values` | `impl-swap-values`: 두 변수의 값을 교환하는 코드 작성 (임시 변수를 스스로 떠올려야 함) | assignment | 3 |
| variables | `fill-price-quantity` | `impl-price-quantity`: `const`/`let`을 골라 결제 금액 프로그램 작성 | const | 3 |

- 없앤 문제의 ID는 다른 곳에서 참조하지 않습니다. `predict-let-reassign`의 기대값은 `content:check:run`이 정리했습니다.
- 숨김 체크(`visible: false`)는 기대 출력이 곧 정답인 문제에만 썼고, `description`으로 무엇을 검사하는지 알립니다.
- 각 핵심 개념(`let`, `assignment`, `const`)은 문제 6개, 서로 다른 변형 그룹 6개를 유지합니다(`variantGroup` 미지정이라 문제마다 별도 그룹).
- `js.mc.let-again-to-change`의 보충 문제에 `impl-change-lives`를 추가했습니다.

- [콘텐츠 작성 가이드](/docs/guides/content-authoring.md)의 "v0.1 콘텐츠에는 `implement_function`이 아직 없다"는 문장을 현재 상태에 맞게 고쳤습니다.

## 남은 한계와 후속 제안

1. **`SyntaxError` 설명이 실제 브라우저와 다릅니다 (러너 쪽 문제).**
   `packages/runner`의 실행 전 문법 검사가 acorn 메시지(`Unexpected token`, `Assigning to rvalue` 등)를 학습자에게 그대로 보여 줍니다.
   초보자에게는 Chrome 메시지가 더 친절하고, 실무에서 보게 될 문장도 Chrome 쪽입니다.
   이번 검토에서는 콘텐츠를 현재 동작에 맞췄습니다(두 문장을 함께 안내).
   러너가 브라우저 엔진의 문법 오류 메시지를 쓰도록 바뀌면, 레슨과 문제의 "ProgInOne에서는 ..." 안내를 다시 정리해야 합니다.
   콘텐츠 범위 밖이라 코드는 고치지 않았습니다.
   - 후속(D-030): 러너가 문법 오류의 문구와 위치를 브라우저 엔진에서 받아 오도록 바뀌었고, 위 안내를 Chrome 문구 하나로 정리했습니다. 다른 브라우저의 문구가 다를 수 있다는 안내는 남겼습니다.
1. **프로그램 작성 문제에서 채점할 수 없는 요구사항이 있습니다.**
   `static` 체크가 아직 서버에 구현되지 않아 "변수를 써서 출력", "글자를 다시 쓰지 말고 대입만으로", "`const`로 만들기"를 강제할 수 없습니다.
   문제 문구는 채점하지 않는 규칙을 필수처럼 말하지 않도록 다듬었고, 해설에서 이유를 설명합니다.
   `static` 체크가 구현되면 `impl-swap-values`, `impl-price-quantity`, `impl-declare-nickname`에 비필수 정적 규칙을 붙이는 것을 권합니다.
1. **reading-errors의 구현 비율이 8%입니다.** 오류 읽기 단원은 진단 성격이라, 정답을 출력하는 문제를 억지로 늘리지 않았습니다. 대신 디버깅·응용 문제(버그 수정 3개)가 그 몫을 합니다.
1. **L4(실전 응용)가 부족하고 L2가 많습니다.** 특히 핵심 단원 variables의 L4는 1개(목표 20%)입니다. 다음 콘텐츠 작업에서 요구사항 해석형 L4 문제나 템플릿을 보강하는 것을 권합니다.
1. **`rubric` 필드가 없습니다.** 설계 문서는 문제마다 루브릭 점수를 원본에 기록하도록 하지만, v0.1 문제에는 없어서 빌드의 난이도 불일치 경고가 동작하지 않습니다. 이번 난이도 판단은 검토자가 루브릭으로 직접 계산했습니다.
1. **복습용 템플릿이 없습니다.** 설계상 주 개념마다(minor 제외) 템플릿 1개 이상이 필요하지만 v0.1에는 템플릿 기능과 원본이 없습니다.
1. **화면에서 확인한 사소한 점**: 레슨의 비교 표에서 좁은 열의 인라인 코드가 줄바꿈됩니다(예: `console.log(3 + 4)`). 읽는 데 지장은 없고 앱 스타일 쪽 문제라 고치지 않았습니다. 레슨 안의 확인 문제(`InlineExercise`)는 아직 "실습 기능과 함께 열려요" 자리 표시로 보입니다.
