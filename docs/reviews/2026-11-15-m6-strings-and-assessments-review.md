검토 절차:

1. 초안 작성 대화를 보지 않았습니다. 원본 파일, 설계 문서, 작성 가이드, 결정 기록, 이전 검토 기록만 읽었습니다.
1. 시작할 때 `pnpm content:check`(오류 0)와 `pnpm content:check:run`(문제 699개, 예제 151개, 실패 0)을 직접 실행했습니다.
1. [품질 체크리스트](/docs/design/content-and-exercises.md#품질-체크리스트-검토자용)를 레슨과 문제마다 확인했습니다. 특히 다음을 봤습니다.
   - 배우기 전 개념을 쓰지 않는지: 모듈 7은 함수(모듈 6) 다음이고, 배열은 모듈 8이라 `split` 결과의 `length`·`[0]`·`join`만 씁니다.
   - 오답 선택지와 `misconception` 연결이 맞는지, 해설이 선택지 글자(a, b…)를 가리키지 않는지(선택지는 섞임)
   - 참/거짓 진술에 굵게 표시가 없는지(진술은 인라인 코드만 렌더링)
   - 난이도 표시가 루브릭 합계와 맞는지
1. **레슨과 해설의 실행 결과를 Node 24 엄격 모드에서 직접 확인했습니다.** 확인한 것은 다음과 같습니다.
   - 문자열 길이(공백·한글 포함), 범위 밖 인덱스의 `undefined`, `str[-1]`
   - 인덱스 대입의 `TypeError: Cannot assign to read only property '0' of string 'cat'`, `"coffee".length()`의 `TypeError`
   - `indexOf`의 `-1`과 처음 위치, 찾기 메서드의 대소문자 구별
   - `slice`의 끝 제외·음수·끝이 시작보다 앞일 때 빈 문자열
   - `trim` 결과 길이, `split`의 조각 수, `join()`의 쉼표, 배열에 `toUpperCase`를 부를 때의 `TypeError`, `trim` 없이 슬러그를 만들 때의 `--my-first-post-`
   - 예측 문제는 `predict-expected.json`의 실행 결과와 해설의 출력을 하나씩 대조했습니다(12개 모두 일치).
1. 평가 문항은 해당 모듈의 연습 문제와 상황·코드 구조가 겹치지 않는지 확인했습니다. 연습 문제를 복사한 문항은 없었습니다.
   - 반복문의 소수 목록(`impl-list-primes`)은 연습 문제 "가장 작은 약수"를 중첩 반복으로 넓힌 것이라 오히려 전이 문제로 봤습니다.
1. 고친 뒤 `pnpm content:check`(오류 0, 범위 안 경고 0)와 `pnpm content:check:run`(실패 0)을 다시 실행했습니다.
1. `pnpm content:build`(승인 문제만)로 빌드하고 앱을 띄워 확인했습니다(`PROGINONE_PORT=4570`, 임시 데이터 폴더, 모의 AI).
   - 레슨 2개를 1280px에서 캡처했습니다. 미렌더링 Markdown, 가로 넘침, 콘솔 오류가 없었습니다.
   - Playwright로 평가 5개를 시작 화면부터 종료 화면까지 한 번씩 풀었습니다. 문항 YAML의 참조 정답을 넣었고, 결과는 [앱 확인](#앱에서-평가-응시)에 있습니다.

## 단원별 판단

### 문자열 다루기 (`string-basics`)

레슨은 표준 12섹션을 모두 갖췄습니다. 인덱스 표, "맨 앞에서 몇 칸" 관점, 반복으로 글자 보기, 엄격 모드의 `TypeError`, 템플릿 리터럴 비교 표가 단순 → 복잡 순서로 이어지고, 오개념 7개가 모두 "흔한 실수"에 있습니다.

고친 것:

- 네 번째 예제 해설: `"2잔이면 " + price * 2`를 "순서 문제"의 예로 들었는데, 이 식은 곱셈이 먼저라 문제가 없습니다. `"합계: " + price + 500`이 `합계: 4500500`이 되는 예로 바꿨습니다(Node로 확인).
- `multi-length-facts`: 정답 "`msg.length`는 5다"를 놓쳤을 때의 오개념이 `last-index-is-length`로 연결되어 있었습니다. 이 정답을 놓치는 이유는 공백을 세지 않은 것이고 마지막 인덱스와는 관계가 없어서, 연결을 지웠습니다.

### 문자열 메서드 (`string-methods` ★)

레슨은 `core` 기준(예제 5개, 그중 예측 3개, 오개념 9개, 실전 사례, 확인 문제 4개)을 채웁니다.
`slice`를 "글자 번호"와 "칸막이" 두 관점으로 설명하고, 배열은 `split` 결과를 다룰 만큼만(`length`, `[0]`, `join`) 소개합니다.

고친 것: 위 표의 `mcq-trim-inner`(다시 씀), `web-nickname-check`(체크 추가), `impl-format-name`(L5 → L4)입니다.

### 조건문 단원 평가 (`control-review`)

평가 개념 6개가 모두 주 개념으로 나옵니다. `if` 2, `else-if` 3, `block` 2, `switch` 3, `fallthrough` 2, `ternary` 3입니다.
`case "S" || "M"`, `if (isVip = true)`, `if (weight > 5);`처럼 처음 보는 함정을 쓰지만, 모두 모듈 3·4에서 배운 규칙으로 풀립니다.
`impl-signup-checks`와 `fix-island-shipping`은 데이터가 잘 골라져 있습니다. `else if` 체인 풀이, 마지막 `else`에 `가입 완료`를 두는 풀이, 출력 금액만 맞추는 풀이를 모두 실패시킵니다.

고친 것: `parsons-pool-entry` 힌트 3 완화, `impl-movie-ticket` L5 → L4.

### 반복문 단원 평가 (`loops-review`)

평가 개념 9개가 모두 주 개념으로 나옵니다. 난이도 분포(L1 2, L2 4, L3 5, L4 3, L5 1)가 평가 목표에 가장 가깝습니다.
`impl-list-primes`(L5)는 지문이 구조를 많이 안내하지만, 루브릭 합계가 10(개념 4개 이상, 상태 시뮬레이션, 프로그램, 플래그 초기화와 `break` 범위의 함정)이라 L5를 유지했습니다.

고친 것: `impl-bus-skip-stops` 지문과 해설, 끝 상태 체크 공개.

### HTML 단원 평가 (`html.semantics.review`)

한 사람의 프로필 페이지라는 한 가지 상황으로 시맨틱 3개념과 제목·이미지·링크를 고르게 확인합니다(개념당 1~4문항).
웹 실습 두 개의 체크는 구조(`body > header.top > h1`, `section.works > div.work-row > article.work`)와 순서(`order`)까지 확인해 `section`·`article` 혼동과 `div`를 모두 바꾸는 과잉 수정을 잡습니다.

고친 것:

- 웹 실습 두 개의 alt 설명 체크(위 표)
- `mcq-profile-nav-link`·`web-work-article`의 지문은 `<!-- 여기 -->` 같은 주석을 인라인 코드로 인용했습니다. 앱 화면에서 코드 글꼴의 합자 때문에 화살표처럼 보여서(`←!— 여기 —→`), "`여기`라고 적힌 주석 자리"처럼 말로 풀었습니다. 코드 블록 안의 주석은 그대로입니다.

### CSS 단원 평가 (`css.layout.review`)

### 연산자 단원 평가 (`operators-review`)

`module.yaml`에 `assessment: operators-review`가 선언되어 있습니다. `itemCount: 18`은 커리큘럼 표의 15보다 많지만 **타당합니다.**
평가 개념이 18개이고 학습 엔진은 개념마다 1문항을 먼저 고르므로, 15로 두면 매번 3개념이 `uncovered`로 남고 `content:check`가 경고합니다(`itemCount`가 개념 수보다 작음).
18은 권장 범위(10~20) 안이고, 이유가 `lesson.yaml` 주석에 적혀 있습니다. `tf-loose-converts`의 진술에서 굵게 표시를 뺀 수정도 확인했습니다(내용 변화 없음).

## 앱에서 평가 응시

승인 문제만 담은 `content.db`로 앱을 띄우고, Playwright가 평가 단원마다 "단원 평가 보기 → 평가 시작 → 문항마다 참조 정답 입력 → 확실해요 → 다음 문제 → 종료 화면"을 진행했습니다.

## 남은 한계

- **재응시 때 같은 문항이 나옵니다.** 네 평가 모두 문항 풀의 크기가 `itemCount`와 같아서, 다시 응시하면 순서만 바뀐 같은 문항이 나옵니다. 조건문 평가를 두 번 응시해 확인했습니다. D-041은 "처음 보는 문항 우선"을 약속하지만 풀이 남지 않습니다. 평가 단원마다 문항을 3~5개 더 쓰면(분리된 2차 검토 필요) 재응시가 달라집니다. 이번 검토에서는 새 문항을 쓰지 않았습니다.
- **풀이 방법은 강제할 수 없습니다.** `static` 체크는 서버 채점이 없어 쓸 수 없습니다. 그래서 "`switch`로 정하세요"(`impl-movie-ticket`), "`while`과 `continue`로"(`impl-bus-skip-stops`), "조건 연산자 하나로"(`impl-concert-labels`), 모바일 우선(CSS 카드 목록) 같은 방법 요구는 결과로만 채점합니다. 지문이나 해설이 이 점을 밝히고 있습니다.
- **프로그램 작성 문제는 입력이 고정입니다.** `entry` 없는 문제(조건문·반복문 평가의 구현 문제)는 시작 코드의 값 하나로만 실행하므로, 기대 출력을 그대로 출력하는 답도 출력 체크는 통과합니다. 대부분 `program` 체크(끝난 뒤의 변수 값)가 이를 일부 막습니다.
- **인라인 코드의 연속 공백이 합쳐집니다**(앱 표시 문제). 정답 판단에 영향을 주는 곳은 고쳤습니다. 레슨의 `"  Coding Bear  ".trim()` 같은 곳은 공백이 하나로 보이지만 의미는 통합니다. 인라인 코드에 `white-space: pre-wrap`을 주는 것은 앱 쪽 작업으로 남깁니다.
- **alt 설명 체크는 낱말 포함만 봅니다.** `배경`처럼 `배`가 들어간 다른 낱말도 통과합니다. 드문 경우라 받아들였습니다.
