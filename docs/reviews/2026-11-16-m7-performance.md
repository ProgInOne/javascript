# M7 성능 점검 (2026-11-16)

PRD 비기능 요구사항 NFR-01~03을 프로덕션 빌드에서 측정한 결과입니다. 로드맵 M7 작업 6, M6 P0 점검의 NFR-01·NFR-02 "측정 없음" 항목을 닫습니다.

- 대상: v0.3.0 이후 `main`(커밋 `f029294` 기준)
- 측정 도구: `pnpm perf`(`e2e/perf.config.ts`, `e2e/perf/`), 결정 [D-064](/docs/decisions.md)
- 결론: **모든 목표를 큰 여유로 만족합니다.** 고칠 회귀는 없고, 느린 컴퓨터에서 여유가 가장 적은 두 곳(학습 화면 첫 진입, 페이지의 첫 코드 실행)을 개선 후보로 남깁니다. 두 곳은 뒤에 고쳤습니다([개선 후 측정](#개선-후-측정-2026-11-16-d-074)).

## 목표

| ID | 항목 | 목표 |
|---|---|---|
| NFR-01 | 앱 첫 화면 표시(로컬) | 2초 이내 |
| NFR-01 | 화면 전환 | 200ms 이내 |
| NFR-01 | 결정론적 채점 결과 표시 | 300ms 이내 |
| NFR-02 | 코드 실행 시작 → 콘솔 첫 출력(일반 예제) | 500ms 이내 |
| NFR-03 | 학습자 코드가 무한 루프여도 메인 UI 응답 | 수치 없음. 이 점검에서는 "가장 긴 프레임 간격 100ms 이하"로 봄(RAIL 응답 기준) |

## 측정 방법

- **환경**: 프로덕션 빌드(`pnpm build`), 실제 콘텐츠 팩(승인된 문제 1,035개, `pnpm content:build`과 같은 빌드), 임시 데이터 위치의 새 학습자(온보딩 완료), 서버 `NODE_ENV=production`, AI는 모의 제공자(Codex를 띄우지 않음). Playwright Chromium, 뷰포트 1440×900.
- **기계**: Apple M1 Pro(10코어), 메모리 16GB, macOS 26(Darwin 25.6), Node.js 24.14.0.
- **측정 구간은 페이지 안에서 잽니다.** 시작은 `window`에서 캡처한 `click`·`keydown` 이벤트(첫 화면은 내비게이션 시작), 끝은 기대한 요소가 문서에 있고 화면에 배치된 첫 `requestAnimationFrame` 콜백 시각(그 프레임을 그리기 직전)입니다. Playwright와 브라우저 사이의 왕복 시간은 들어가지 않으며, 오차는 최대 한 프레임(약 16ms)입니다.
- **"표시됨"의 기준**
  - 화면: 그 화면의 `h1`이 새로 나타나고, 로딩 자리 표시(`.pi-skeleton`, `aria-busy="true"`)가 하나도 없음. 즉 데이터를 받아 그린 뒤입니다.
  - 채점: 피드백 제목("정답이에요." 등)이 나타남.
  - 콘솔: 이번 실행이 출력한 첫 줄이 콘솔에 나타남.
- **반복**: 항목마다 5회(`PERF_ROUNDS`), 중앙값을 목표와 비교합니다. 첫 방문(코드 조각과 데이터를 처음 받음)과 재방문을 나눠 봅니다.
- **시나리오**
  - 첫 화면: 새 브라우저 컨텍스트(HTTP 캐시 비어 있음)에서 `/` → 대시보드. 같은 컨텍스트에서 새로 고침도 잼.
  - 화면 전환: 대시보드 → 과정 → 과정 상세(JavaScript 기초) → 레슨(첫 프로그램) → 과정 상세 → 복습 → 설정 → 대시보드를 5바퀴. 링크·버튼 클릭으로만 이동.
  - 결정론적 채점: 실제 콘텐츠의 객관식 3, 다중 선택 2, 참/거짓 2, 출력 예측 3문제를 "다시 풀기"(`extra`) 세트로 열어 답을 고르고 "확실해요" → 피드백. 정오답은 시간과 무관해서 첫 보기를 고릅니다.
  - 콘솔 첫 출력: 실제 콘텐츠의 고쳐 쓰기(`fix_bug`, js-console) 3문제에서 일반 예제(5줄, 반복문 포함)로 바꿔 "실행"을 5번씩. 각 실행은 첫 줄에 실행 번호를 출력해 이전 실행의 줄과 구분합니다.
  - 무한 루프: `console.log("start"); while (true) {}`를 실행하고, 러너가 멈출 때까지 앱 문서의 가장 긴 프레임 간격을 잼.
- 느린 컴퓨터의 여유를 보려고 DevTools CPU 4배 감속(`PERF_CPU_THROTTLE=4`)으로도 한 번 측정했습니다. 네트워크는 로컬이라 감속하지 않습니다.

다른 관찰:

- 무한 루프는 러너의 반복 감시가 1.3초 만에 멈추고 "반복이 너무 오래 실행되어 멈췄어요 (2번째 줄)"을 표시합니다. 그동안 앱은 매 프레임(17ms) 그렸습니다. 학습자 코드는 별도 프로세스의 셸에서 돌기 때문입니다(D-018).
- 첫 화면은 JS 39개 파일(압축 해제 683KB)을 받습니다. DOMContentLoaded 47~83ms, 첫 콘텐츠 페인트 120~200ms이고, 나머지는 API 응답(대시보드 데이터)을 기다리는 시간입니다.
- 측정을 반복하면 1배 기준 값이 ±50% 안팎으로 흔들렸습니다(예: 대시보드 → 과정 첫 방문 61~206ms, 첫 화면 142~373ms). 모두 목표 안이지만, 이 흔들림 때문에 시간 기준은 CI에 넣지 않았습니다(D-064).

## 첫 화면 번들 예산 (CI)

시간 대신 결정론적인 바이트 수로 첫 화면 회귀를 막습니다. `pnpm check:bundle`(`tools/check-bundle.mjs`)이 `apps/web/dist/index.html`이 첫 화면 전에 받는 파일(진입 스크립트, `modulepreload` 조각, 스타일시트)의 gzip 크기를 더해 예산과 비교하고, CI `check` 작업이 빌드 직후 실행합니다.

| 종류 | 현재(gzip) | 예산 | 주요 구성 |
|---|---|---|---|
| JS | 190KiB(16개 파일) | 220KiB | `react-dom`, 라우터, TanStack Query, zod(`@proginone/shared` API 스키마) |
| CSS | 36KiB(1개 파일) | 45KiB | Tailwind 유틸리티, Pretendard `@font-face` 하위 집합 선언 |

예산은 현재보다 15~25% 높게 잡았습니다. 넘으면 가장 큰 파일 5개를 출력하고 실패합니다. 예산을 올릴 때는 PR에 이유를 씁니다.

## 개선 후보 (점검 당시 고치지 않음)

1배 기준으로 모든 목표를 5배 이상 여유로 만족하므로 이번에는 고치지 않았습니다. 4배 감속에서 여유가 가장 적은 곳입니다.

| 후보 | 근거 | 제안 | 예상 규모 |
|---|---|---|---|
| 학습 화면 코드 조각이 1MB(gzip 329KB) | 과정 상세 → 레슨 첫 방문 134ms(4배: 703ms). 조각에 CodeMirror(약 1MB 원본), 러너 준비 단계의 `parse5`·`acorn`(원본 약 550KB), `exercise-kit`이 함께 있음 | 러너 준비 모듈(`packages/runner/src/prepare`)을 동적 `import()`로 나누고 학습 화면이 뜬 뒤 유휴 시간에 미리 받기. 읽기 모드에서는 CodeMirror도 늦게 받기 | 반나절 |
| 페이지의 첫 코드 실행 240ms(4배: 842ms) | 셸 iframe(`*.localhost` 사이트) 생성과 첫 Worker 준비가 첫 실행에 몰림 | 실습 화면이 뜨면 셸을 미리 만들어 두기(`RunnerHost.ready()` 선행 호출) | 2시간 |
| 무한 루프 중 프레임 간격(4배: 133ms) | 1배는 17ms. 감속 시 실행 결과 처리·렌더링이 한 프레임을 넘김 | 위 두 항목 뒤 다시 측정. 학습자 기기 기준(최근 Mac)에서는 문제 없음 | — |

## 개선 후 측정 (2026-11-16, D-074)

위 후보 중 앞의 두 개를 반영했습니다([D-074](/docs/decisions.md)).

- 러너 준비 단계(parse5·acorn)를 동적 `import()`로 나눴습니다. 학습 화면 조각이 1,015KB(gzip 330KB)에서 **724KB(gzip 246KB)**로 줄고, 준비 단계는 첫 실행 전에 받는 별도 조각(291KB, gzip 83KB)이 됐습니다. 첫 화면 번들(`pnpm check:bundle`, JS 190.7KiB)은 그대로입니다.
- 실습 문제·프로젝트·레슨 예제 화면이 뜨면 유휴 시간에 준비 단계를 받고 공유 숨김 셸을 연결합니다(`warmRunner`). 첫 "실행"이 셸 생성과 준비 단계 로드를 기다리지 않습니다.
- CodeMirror 지연 로드는 하지 않았습니다(D-074의 이유). 학습 화면 조각의 나머지 대부분이 CodeMirror입니다.

같은 기계에서 CPU 4배 감속(`PERF_CPU_THROTTLE=4`)으로 고치기 전(`bfaa9eb` 빌드)과 고친 뒤를 **번갈아 세 번씩** 쟀습니다(같은 포트·같은 콘텐츠 팩, 한 번에 하나씩). 측정하는 동안 다른 작업이 같은 기계에서 돌아 load average가 16~27이었습니다. 단위는 ms이고, 각 칸은 세 번 측정 값(각 측정은 항목의 중앙값, 첫 실행과 첫 방문은 1회 값)과 그 중앙값입니다.

| 항목 | 고치기 전(4배) | 고친 뒤(4배) |
|---|---|---|
| 콘솔 첫 출력(페이지의 첫 실행) | 873 · 334 · 378 → **378** | 149 · 207 · 173 → **173** |
| 콘솔 첫 출력(셸 준비 후) | 96 · 105 · 107 → 105 | 106 · 113 · 101 → 106 |
| 과정 상세 → 레슨 첫 방문 | 644 · 430 · 791 → 644 | 723 · 820 · 498 → 723 |
| 화면 전환(첫 방문, 전체) | 92 · 77 · 106 → 92 | 95 · 113 · 75 → 95 |
| 무한 루프 중 가장 긴 프레임 간격 | 67 · 83 · 50 → 67 | 50 · 117 · 67 → 67 |
| 첫 화면(빈 캐시) | 828 · 868 · 942 → 868 | 974 · 965 · 929 → 965 |

- **페이지의 첫 실행은 목표(500ms) 안으로 안정적으로 들어왔습니다**(고치기 전 한 번은 873으로 목표 초과). 셸을 미리 연결해 두어 셸 준비 후 실행과의 차이가 약 70ms로 줄었습니다.
- **과정 상세 → 레슨 첫 방문은 줄지 않았습니다.** 조각은 gzip 84KB 작아졌지만 로컬 서버라 내려받는 시간이 거의 없고, 이 구간은 주로 JS 해석·실행과 화면 그리기라 남은 CodeMirror가 대부분을 차지합니다. 세 번 사이의 흔들림(430~820)이 차이보다 커서 나빠졌다고도 보지 않습니다. 이 구간을 줄이려면 CodeMirror 지연 로드가 필요합니다(후속).
- 첫 화면은 이번 변경과 무관합니다(첫 화면 번들이 같음). 값의 차이는 부하에 따른 흔들림 범위입니다.
- 먼저 한 번씩만 잰 측정(load average 60~190)에서는 첫 실행이 1,589 → 199였지만, 부하가 크게 달라 위의 번갈아 잰 값으로 판단합니다.

## 다시 측정하는 법

```shell
pnpm perf                                            # 빌드 후 측정, 목표 미달이면 실패
PERF_CPU_THROTTLE=4 pnpm --filter @proginone/e2e perf   # 4배 감속(빌드는 먼저)
```

결과 JSON은 `e2e/perf-results/`에 남습니다. 측정 방법은 [테스트 가이드 성능 측정](/docs/guides/testing.md#성능-측정)에 있습니다.
