검토 방법, 단원별 판단, 직접 고친 내용, 최종 문제 구성과 남은 한계를 적습니다.

- 검토: 독립 AI 검토자 (`ai:reviewer`, [D-027](/docs/decisions.md))
- 검토일: 2026-11-15
- 관련 문서: [콘텐츠·문제 시스템 설계](/docs/design/content-and-exercises.md), [콘텐츠 작성 가이드](/docs/guides/content-authoring.md), [결정 기록](/docs/decisions.md), [v0.1 콘텐츠 검토](/docs/reviews/2026-11-15-v0.1-content-review.md)

## 검토 범위와 방법

대상은 `content/courses/html/`의 3개 모듈 7개 단원, `content/concepts/html.yaml`(개념 23개), `content/misconceptions/html.yaml`(오개념 26개)입니다.
모든 문제가 `review.status: draft`, `draftedBy: ai:claude`였습니다.
단원 평가(`html.semantics.review`)는 M6에서 추가되므로 이번 범위에 없습니다.

| 단원 | 중요도 | 목표 문제 수 |
|---|---|---|
| `html.basics.how-web-works` 브라우저는 무엇을 하는가 | standard | 6 |
| `html.basics.document` HTML 문서의 뼈대 | standard | 10 |
| `html.basics.text` 텍스트와 제목 | standard | 8 |
| `html.content.links-images` 링크와 이미지 | standard | 9 |
| `html.content.lists-tables` 목록과 표 | standard | 8 |
| `html.content.forms` 폼 기초 | standard | 10 |
| `html.semantics.landmarks` 시맨틱 태그 | standard | 10 |

전체 수가 적어서 샘플링 없이 **레슨과 문제를 모두 검토**했습니다.

검토 절차:

1. 초안 작성 대화를 보지 않고, 원본 파일과 설계 문서·작성 가이드·결정 기록(D-026~D-039)·v0.1 검토 기록만 읽었습니다.
1. 검토 시작 전에 `pnpm content:check`(오류 0)와 `pnpm content:check:run`(실패 0)을 직접 실행했습니다.
1. 레슨마다 [품질 체크리스트](/docs/design/content-and-exercises.md#품질-체크리스트-검토자용)의 레슨 항목, 표준 섹션 12종, 선수 개념 순서를 확인했습니다. 특히 HTML 명세·MDN과 맞는지, 접근성 설명(대체 텍스트, label 연결, 랜드마크)이 정확한지 봤습니다.
1. 문제마다 체크리스트의 문제 항목을 확인했습니다. 특히 다음을 봤습니다.
   - `web_task`·코드 빈칸의 체크가 요구사항을 실제로 검사하는지, 시작 코드와 뻔히 틀린 마크업을 거부하는지
   - 아직 배우지 않은 개념을 쓰는지, 오답 선택지와 `misconception` 연결의 방향이 맞는지
   - 힌트 3단계가 점진적이고 3단계가 정답을 그대로 주지 않는지
   - 난이도가 [루브릭](/docs/design/content-and-exercises.md#난이도-루브릭) 합계와 맞는지
1. 앱의 알려진 한계를 피했는지 확인했습니다. `expect.order`만 있는 `dom` 체크(항상 실패)는 두 문제 모두 `tag`를 함께 써서 피하고 있었고, `html-valid`·`static` 체크에 기대는 문제는 없었습니다. 링크·폼 이동에 기대는 문제도 없습니다.
1. `content:build:dev`로 빌드하고 앱(`PROGINONE_PORT=4495`, 임시 데이터 디렉터리)을 띄워 레슨 7개를 Playwright로 캡처했습니다. 실습 모드에서 단원마다 연습 세트를 끝까지 넘기며 모든 문제의 화면을 확인했고, **웹 실습 13개는 시작 코드 화면을 캡처한 뒤 참조 정답을 입력해 앱이 실제로 정답 처리하는지** 확인했습니다(13개 모두 정답).
   링크를 누를 때, 폼을 보낼 때, 깨진 그림과 `alt`가 어떻게 보이는지도 레슨 예제에서 직접 실행해 봤습니다.
1. 수정 뒤 `pnpm content:check`(HTML 경고 0)와 `pnpm content:check:run`(실패 0)을 다시 실행했습니다. HTML에는 `predict_output`이 없어 `predict-expected.json`은 바뀌지 않았습니다.

### 검토자가 직접 쓴 문제의 2차 검토

유형 구성을 맞추려고 새로 쓴 6문제(아래 [유형 구성 조정](#유형-구성-조정))는 검토자 자신이 쓴 문제입니다.
자기 승인을 피하기 위해, **분리된 컨텍스트의 2차 AI 검토자**에게 이 6문제만 다시 검토하게 했습니다.

2차 검토는 6문제 중 3개(`fill-img-alt`, `fill-wrap-list`, `fill-email-type`)를 그대로 승인하고 3개에 수정을 요청했습니다.
요청 내용은 모두 반영한 뒤 승인했습니다.

- `fill-dom-repair`: "DOM 트리에 생기는 `p`의 수"는 세 문단이 서로 안에 중첩된다고 생각하는 학습자도 3이라고 답해서, 노리는 오개념을 가려내지 못했습니다. "`body`의 자식인 `p`의 수"로 바꿔 오개념이면 1이 되게 했습니다. `body` 빈칸의 허용 답에 "있음", "있습니다"를 더했습니다.
- `fill-paragraph-count`: 힌트 2("`p`가 몇 개인지 세어 보세요")가 힌트 3보다 더 직접적이라 두 힌트의 순서를 바꿨습니다. 나올 수 없는 오답 "4"의 오개념 연결을 지웠습니다.
- `fill-layout-div`: "`article`로 감싸면 화면 낭독기가 있지도 않은 글이 있다고 알린다"는 해설이 과장이라는 지적(글 안에 글을 넣는 것 자체는 올바른 HTML)에 따라 "독립된 글이라는 틀린 뜻이 붙는다"로 고쳤습니다.

`draftedBy`는 스키마 형식(`ai:<제공자>`)에 따라 `ai:claude`로 두었습니다.
이 6문제를 검토자가 썼다는 사실은 이 기록과 git 이력에 남습니다.

## 단원별 검토 요약

전체적으로 초안의 품질이 높았습니다. 설명이 대부분 정확하고, 오개념 26개가 모두 레슨의 "흔한 실수"에 있으며, 웹 실습의 체크가 시작 코드를 거부하고 정답을 받아들였습니다.
주된 수정은 ① 앱 동작에 기대는 문구, ② 접근성 설명의 부정확한 부분, ③ 정답을 그대로 주는 힌트 3단계, ④ 난이도 과대 표시, ⑤ 개념 확인 유형 쏠림이었습니다.

### html.basics.how-web-works

레슨과 문제 6개를 승인했습니다.

- `mcq-tags-not-shown`: 태그가 화면에 보이지 않는다는 회상 문제라 난이도 2 → 1(루브릭 합 2).
- `web-first-page`: 힌트 3이 두 문장의 정답 태그를 그대로 줬습니다. 여는 태그·닫는 태그를 쓰는 방법만 알려 주도록 고쳤습니다.
- 개념 확인 유형이 5/6입니다. 첫 단원이고 코드가 거의 없는 개념 단원이라 바꾸지 않았습니다.

### html.basics.document

레슨과 문제 10개를 승인했습니다.

- 레슨: DOM 트리 그림 앞의 "위의 뼈대에 문단 하나를 더하면"은 그림에 있는 `strong`이 어디서 왔는지 알 수 없어 "안에 `strong`이 든 문단 하나를"로 고쳤습니다.
- `fill-close-nested`: 난이도 3 → 2(루브릭 합 4). 빈칸 순서가 내용("체육복"만 강조)으로 거의 정해집니다.
- `web-skeleton`: 힌트 3이 `<title>자기소개</title>`를 그대로 줬습니다. 넣을 위치와 속성 쓰는 형태만 알려 주도록 고쳤습니다.
- `tf-dom-is-source`를 코드 이해 문제 `fill-dom-repair`로 바꿨습니다(아래 표).

### html.basics.text

레슨과 문제 8개를 승인했습니다. 레슨은 고칠 것이 없었습니다.

- `fill-strong-warning`: 힌트 3이 `strong`을 그대로 말했습니다. 이름의 뜻("강한")만 알려 주도록 고쳤습니다. 해설의 "`<b>`는 뜻 없이"를 "중요하다는 뜻 없이"로 고쳤습니다(`b`도 HTML 명세상 뜻이 아주 없지는 않습니다).
- `tf-newline-in-source`를 `fill-paragraph-count`로 바꿨습니다. `mcq-whitespace-render`와 같은 내용을 묻는 참/거짓이었습니다.

### html.content.links-images

레슨과 문제 9개를 승인했습니다.

- **앱 동작에 기대는 문구를 고쳤습니다.** 레슨과 `web-club-links`가 "미리보기에서 링크를 누르면 빈 화면이 된다"고 단정했습니다. 미리보기의 이동 처리는 개발 중이라 바뀔 수 있으므로 "다른 페이지로 이동하지 않아요. 미리보기 모양이 바뀌면 다시 실행하세요"로 고쳤습니다.
- `web-image-alt`: 상품 사진의 `alt` 체크가 "비어 있지 않음"뿐이라 `alt="사진"`도 통과했습니다. 해설이 "사진"만 쓰면 안 된다고 하는 것과 어긋나므로, `alt`에 상품 이름(`컵`·`잔`·`mug`)이 들어 있는지 보는 공개 체크 `product-alt-names`를 더했습니다. 힌트 3이 정답 `alt` 두 개를 그대로 줬고 그 예시가 해설과 달리 "사진"을 포함해서, 쓸 내용만 설명하도록 고쳤습니다.
- `web-club-links`: 같은 형태의 링크 세 개를 만드는 기계적인 작업이고 힌트 3이 첫 링크를 그대로 줘서 난이도 3 → 2.
- `mcq-parent-folder-path`: 한 개념, 여러 단계 경로 추적, 오개념 두 개(루브릭 합 4)라 난이도 3 → 2.
- `tf-img-content`를 `fill-img-alt`로 바꿨습니다. 원래 문제의 이유 선택지 r3("img에는 닫는 태그가 있지만 설명을 쓸 방법이 없다")에 `alt-optional`이 붙어 있었는데, 실제로 드러나는 오개념은 `img-has-content`입니다.

### html.content.lists-tables

레슨과 문제 8개를 승인했습니다.

- 레슨: "화면 낭독기는 `td`를 읽을 때 그 열의 `th`를 함께 읽어 준다"는 표 탐색 중에 칸을 옮길 때의 동작이라 "표의 칸을 옮겨 다니며 `td`를 읽을 때"로 고쳤습니다.
- `fill-table-size`: 힌트 3이 "제목 행 1개 + 데이터 행 3개, 칸은 2개씩"으로 사실상 답이었습니다. 세는 방법만 알려 주도록 고쳤습니다.
- `web-exercise-table`: 난이도 4 → 3. 표를 처음부터 쓰는 이 과정에서 가장 큰 작업이지만, 요구사항이 단계별로 다 주어져 있어 해석이 필요한 L4(루브릭 합 7~9)는 아닙니다(합 6).
- `tf-li-alone`을 `fill-wrap-list`로 바꿨습니다.

### html.content.forms

레슨과 문제 10개를 승인했습니다.

- **앱 동작에 기대는 문구를 고쳤습니다.** 레슨 두 곳과 `web-search-form`·`web-signup-types`가 "폼을 보내면 미리보기가 빈 화면이 되고 실제 전송은 막혀 있다"고 단정했습니다. "미리보기는 폼을 실제로 전송하지 않아요. 미리보기 모양이 바뀌면(빈 화면이나 안내) 다시 실행하세요"로 고쳤습니다. 지금 앱에서는 빈 화면이 되는 것을 확인했습니다.
- 레슨: `action="/search"`처럼 `/`로 시작하는 경로를 설명 없이 썼습니다. 앞 단원은 절대 경로(`https://`)와 상대 경로(지금 폴더 기준)만 다뤘으므로, "`/`로 시작하는 경로는 사이트의 맨 위 폴더에서 출발한다"는 한 문장을 `action` 설명에 더했습니다.
- `web-signup-types`: 힌트 3이 "각각 `email`, `password`, `number`예요"로 정답 그대로였습니다. 영어 낱말이라는 단서만 주도록 고쳤습니다. `web-search-form`의 힌트 3도 정답 코드 대신 위치와 값만 알려 주도록 고쳤습니다.
- `web-connect-labels`: `for` 두 개를 더하는 작업이라 난이도 3 → 2(루브릭 합 4).
- `multi-type-effects`: 선택지의 "(예. `email`)"을 "(예: `email`)"로 고쳤습니다.
- `mcq-email-type`을 `fill-email-type`으로 바꿨습니다. `multi-type-effects`, `web-signup-types`와 내용이 겹치는 선택형이었습니다.

### html.semantics.landmarks

레슨과 문제 10개를 승인했습니다.

- **접근성 설명의 부정확한 부분을 고쳤습니다.**
  - 레슨·`tf-div-is-wrong`·`web-blog-structure`가 "배치용 상자를 `section`으로 바꾸면 화면 낭독기에 이름 없는 구역이 생긴다"고 했습니다. 이름(접근 가능한 이름)이 없는 `section`은 화면 낭독기에 구역(region)으로 알려지지 않습니다. 실제로 화면 낭독기가 알리는 `article`(글)을 예로 들고, `section`은 "주제별 구역이라는 틀린 뜻이 붙는다"로 고쳤습니다.
  - 레슨: `footer` 랜드마크의 이름을 "정보"에서 화면 낭독기가 쓰는 "콘텐츠 정보"로 고쳤습니다.
  - 레슨: `header`·`footer`가 `article` 안에서는 페이지 랜드마크가 아니라 그 글의 머리말·꼬리말이라는 문장을 더했습니다. `mcq-article-or-section` 해설이 "기사 제목 부분을 article 안에서 header로 감쌀 수 있다"고 하는데 레슨에는 그 설명이 없었습니다.
  - 레슨: "검색 엔진도 `main`과 `article`을 보고 핵심 내용을 찾는다"는 단정을 "검색 엔진이나 읽기 모드 같은 프로그램도 단서로 쓸 수 있다"로 완화했습니다.
- `mcq-article-or-section`: 오답 `div`에 `div-is-wrong`("div를 쓰면 안 된다") 오개념이 붙어 있었는데, 기사에 `div`를 고르는 것은 반대 방향의 실수라 연결을 지웠습니다.
- `web-page-landmarks`, `web-blog-structure`: 힌트 3이 남은 요소 이름이나 바꿀 코드 전체를 그대로 줬습니다. 단서와 닫는 태그 확인 방법만 주도록 고쳤습니다.
- `tf-div-is-wrong`을 `fill-layout-div`로 바꿨습니다. `mcq-div-when`과 같은 내용을 묻는 참/거짓이었습니다.

### 개념·오개념 파일

- 개념 ID는 바꾸지 않았습니다(CSS 과정이 선수 개념으로 참조할 수 있음).
- 오개념의 보충 문제 목록(`remediation.exercises`)을 바꾼 문제 ID에 맞췄습니다. `input-type-looks-only`에는 `fill-email-type`을 더했습니다.

## 유형 구성 조정

검토 전 61문제 중 개념 확인 유형(단일·복수 선택, 참/거짓)이 40개(66%)로, HTML/CSS 목표(개념 확인 35% · 코드 이해 25% · 디버깅 10% · 구현 30%, ±10%p)에서 크게 벗어났습니다. 코드 이해(빈칸)는 8개(13%)였습니다.
같은 단원의 다른 문제와 내용이 겹치는 선택형 6개를 빈칸 문제로 바꿨습니다. 유형은 HTML 핵심의 허용 범위(선택형·빈칸·웹 실습) 안에서 골랐습니다.

## 남은 한계와 후속 제안

1. **개념 확인 유형이 여전히 많습니다(56%, 목표 35% ± 10%p).** 첫 단원(how-web-works)은 코드가 거의 없는 개념 단원이라 83%입니다. 문제를 더 바꾸면 검토자가 쓴 문제의 비중이 커져서 이번에는 6개만 바꿨습니다. 단원 평가를 쓰는 M6에서 웹 실습·빈칸 위주로 보강하거나, 남은 참/거짓 일부를 웹 실습으로 바꾸는 것을 권합니다.
1. **L3·L4가 부족합니다(L3 11%, L4 2%).** 초안의 L3 다수가 루브릭상 L2였습니다. 요구사항을 해석해야 하는 웹 실습(예: 주어진 글을 보고 제목 계층·목록·표를 스스로 고르는 문제)을 M6 단원 평가에서 보강하는 것을 권합니다.
1. **숙련 단계 게이트를 채울 수 없는 개념이 있습니다.** 설계상 주 개념마다 개념 이해·코드 이해·실습 유형이 하나씩, L3 이상 문제가 하나 있어야 하지만, HTML 핵심은 개념당 2문제의 얕은 구성이라 대부분의 개념이 이를 채우지 못합니다(예: `client-server`는 선택형 2개). `depth: core`의 의도된 한계로 보고 그대로 두었습니다.
1. **채점할 수 없는 부분이 있습니다.**
   - `fill-faq-section`(코드 빈칸)은 닫는 태그 빈칸에 다른 이름을 써도 브라우저가 구조를 고쳐서 같은 DOM이 되므로 통과합니다. DOM 체크로는 구별할 수 없어 그대로 두었습니다(`html-valid` 체크가 서버에서 계산되면 보강할 수 있습니다).
   - `fill-wrap-list`도 여는 빈칸에 `ul`, 닫는 빈칸에 `ol`을 쓰면 브라우저가 짝이 안 맞는 닫는 태그를 무시해서 통과합니다(2차 검토 지적, 같은 이유로 그대로 둠).
   - `web-image-alt`의 `alt`가 "좋은 설명"인지는 상품 이름이 들어 있는지까지만 확인합니다.
1. **앱 쪽에서 본 점(코드는 고치지 않음)**
   - 미리보기에서 링크를 누르거나 폼을 보내면 지금은 미리보기가 빈 화면이 됩니다. 레슨과 문제는 이 동작에 기대지 않게 고쳤습니다. 이동 처리가 바뀌면 "미리보기 모양이 바뀌면(빈 화면이나 안내)" 문구를 새 동작에 맞춰 다듬으면 됩니다.
   - `expect.order`만 있는 `dom` 체크가 항상 실패하는 문제 때문에 `web-heading-outline`·`web-page-landmarks`의 순서 체크에 `tag: body`를 함께 둡니다. 고쳐진 뒤에도 그대로 동작합니다.
   - 실습 모드에서 문제의 `code` 필드(지문에 딸린 코드)가 "출력"이라는 머리글 아래에 보입니다(`apps/web`의 `Markdown.tsx`가 언어 없는 코드 블록을 "출력"으로 표시). HTML 코드나 폴더 구조가 실행 결과처럼 보여 초보자에게 헷갈릴 수 있으니, 지문 코드는 "코드" 같은 머리글로 바꾸는 것을 권합니다. JS 과정의 문제에도 같은 영향이 있습니다.
   - 레슨 예제의 미리보기가 세리프 글꼴로 그려지고, 실습 화면을 전체 페이지로 캡처하면 고정 헤더가 중간에 찍힙니다. 읽는 데 지장은 없습니다.
1. **`rubric` 필드가 없습니다.** v0.1 검토와 같이, 난이도 판단은 검토자가 루브릭으로 직접 계산했습니다.
1. **복습용 템플릿이 없습니다.** 템플릿 기능이 아직 없어 v0.1과 같은 한계입니다.
