## D-010. AI 튜터 개입 정책 — `확정`
- 정답 공개 여부는 **프롬프트가 아니라 코드가 결정**합니다. 힌트 단계에 따라 AI 컨텍스트에 정답 포함 여부를 제어합니다.
- 힌트 3단계 (방향 제시 → 핵심 개념/부분 코드 → 거의 완성된 가이드) 이후 명시적 "정답 보기" 행동으로만 정답 공개. 정답 열람 시 숙련도 반영 가중치 감소.
- 소크라테스식 질문 유도를 기본으로 하되, 학습자가 연속으로 막히면 직접 설명으로 전환.
- 튜터의 선제 개입은 제한적으로: 반복 실패, 장시간 정체, 확신했는데 틀린 경우에만 제안 형태(배지/버튼)로 표시하고 대화를 강제로 열지 않습니다.
- AI는 학습자 모델에 직접 쓰지 않고, 근거가 있는 "제안"만 하며 앱이 검증 후 반영합니다.

## D-018. 샌드박스 러너 셸 방식 — `확정`
- 2026-11-14 사용자 승인. M1-B PoC(Chromium, Chrome, Firefox, WebKit) 결과를 반영해 2026-11-14 확정했습니다.
- 서버가 `/sandbox/runner.html`을 전용 CSP 응답 헤더와 함께 제공하고, 앱은 `sandbox="allow-scripts allow-forms"` iframe으로 삽입합니다.
- 앱 문서에서 직접 `srcdoc` iframe을 만들지 않습니다. `srcdoc` 문서는 부모의 CSP를 상속하므로 러너 전용 정책(`connect-src 'none'` 등)을 독립적으로 줄 수 없기 때문입니다.
- 순수 JS는 셸 내부 Worker(`terminate()`로 중단), DOM·미리보기는 셸 내부 중첩 iframe + 루프 가드 + 워치독으로 실행합니다.
- 채점은 관측 모델입니다: 하네스는 관측값만 반환하고 서버가 기대값과 비교합니다.
- **PoC 보완 (확정 시 추가)**:
  - 셸은 실행 환경마다 다른 서브도메인 `http://<shellId>.localhost:<port>/sandbox/runner.html`에서 엽니다. 멈춘 셸 프로세스를 다음 실행이 재사용하지 않고, Firefox에서 앱 탭이 함께 멈추는 문제를 막습니다. 3초 안에 `shell-hello`가 오지 않으면 같은 사이트 경로로 대체합니다.
  - 서버는 `*.localhost` 호스트로 들어온 요청에 `/sandbox/runner.html`과 그 자산만 제공합니다. 앱 CSP는 `frame-src 'self' http://*.localhost:<port>`를 허용합니다.
  - 인라인 스크립트는 blob 스크립트로 전달해 WebKit의 `"Script error."` 마스킹을 피합니다.
  - Worker 범위에서 `EventSource`, `Worker`, `SharedWorker`를 제거하고, 학습자 문서에는 `worker-src 'none'`을 겁니다.
  - 남은 위험: WebKit은 루프 가드가 동작해도 앱 탭이 약 1초 멈출 수 있습니다. 실제 Safari의 `*.localhost` 처리는 M3에서 다시 확인합니다.
- 상세: [코드 실행 샌드박스 설계](/docs/design/code-execution-sandbox.md).

- 영향: 비엄격 모드에 기대던 콘텐츠는 실행 검증(`pnpm content:check:run`)에서 드러납니다. `var`와 비엄격 모드의 차이는 "`var`와 선언 전 사용" 단원에서 설명합니다.
- 상세: [코드 실행 샌드박스 설계](/docs/design/code-execution-sandbox.md#엄격-모드-기본-적용).

## D-030. 러너 문법 오류 메시지 — `확정`
- 2026-11-15, 사용자가 위임한 결정.
- 학습자에게 보여 주는 `SyntaxError` 문구를 **브라우저 엔진의 원래 메시지**로 맞춥니다. 지금은 러너의 사전 구문 검사기(acorn) 문구(`Unexpected token` 등)가 보여서, 레슨이 가르치는 Chrome 메시지(`missing ) after argument list` 등)와 다릅니다. 사전 검사에서 실패하면 계측 없이 원본을 샌드박스에서 실행해 엔진이 낸 `SyntaxError`와 위치를 그대로 쓰는 방식으로 M5에서 구현하고, 레슨의 "ProgInOne에서는 …" 안내를 함께 정리합니다.
- 근거: 학습자가 실제 브라우저 개발자 도구에서 보게 될 문구와 같아야 오류 읽기 학습이 전이됩니다.
- 구현: 사전 검사가 실패하면 Host가 실패한 스크립트만 담은 **엔진 문법 검사**(`syntaxOnly`인 `dom` 실행)를 셸에 보냅니다. 검사 스크립트는 `'use strict';throw 0;` 뒤에 원본을 같은 줄로 붙여(핸들러는 함수 본문으로 감싸서) 엔진이 받아들여도 학습자 코드가 실행되지 않습니다. 엔진의 `SyntaxError` 메시지와 위치를 학습자 파일로 되돌려 `phase: 'syntax'`로 보고하고, 엔진이 오류를 내지 않으면 acorn 문구로 대체합니다. `js-console`도 문서에서 검사합니다(Worker `importScripts`는 위치를 주지 않음). 상세: [코드 실행 샌드박스 설계](/docs/design/code-execution-sandbox.md#문법-오류).

## D-031. 파슨스 문제의 공개 ID·채점·키보드 조작 — `확정`

- **공개 ID는 저작 ID의 해시**입니다. 저작자는 `l1`…`l7`, `d1`처럼 순서와 방해 줄을 드러내는 ID를 쓰기 쉬워서, 클라이언트에는 해시만 보냅니다. 조각은 시드가 없어도 섞고, 정답 순서로 섞이면 한 칸 돌립니다. 보안이 아니라 D-010(힌트 정책)이 개발자 도구 습관으로 무력화되지 않게 하는 설계 원칙입니다.

- 2026-11-15, 사용자가 위임한 결정(M5 학습 엔진 확장, 권장안대로 진행).
- **오개념에는 "해소 중" 상태를 두지 않습니다.** 상태는 설계 문서의 네 가지(`suspected`, `confirmed`, `resolved`, `dismissed`)이고, 해소까지의 진행은 `misconception_observations.resolution_attempt_ids_json`(마지막 근거 이후 겨냥 문제 첫 시도 정답)으로 보여 줍니다. API는 `resolution: { done, required }`를 함께 내려, 화면이 "해소 중(1/2)"처럼 표시할 수 있습니다. 근거: 상태를 늘리면 부분 고유 인덱스·전이 표·재계산 규칙이 함께 늘지만, 진행도로 같은 정보를 줄 수 있습니다.
- **오개념 행은 다시 엽니다.** `resolved`·`dismissed` 뒤의 새 근거는 새 행이 아니라 같은 행의 상태를 바꿉니다. 재발 횟수는 `confirm_count`로 셉니다.
- **재학습 제안을 기록합니다**(`remediation_suggestions`, 데이터 모델에 추가). "최근 점검한 선수 개념은 다시 점검하지 않음", "풀이 예제는 다음 단계부터", "예제 2단계 뒤에도 실패하면 레슨 다시 읽기"를 판정하려면 이전 제안을 알아야 하기 때문입니다. 같은 세트에서 같은 개념의 제안은 앞선 제안을 다 풀기 전에는 다시 만들지 않습니다.
- **"같은 세트 오답 2연속"은 항목 단위**로 셉니다. 같은 항목을 다시 틀린 것은 새로운 독립 증거가 아니라는 `W_try`의 전제와 맞춥니다.
- **재학습 항목은 거절할 수 있게 세트 끝에 붙입니다.** 제안이 나오면 항목을 바로 세트 끝에 붙이고 응답에 항목 ID를 줍니다. "선수 개념 확인하기"는 그 항목으로 건너뛰고, "계속 풀기"는 원래 순서대로 진행합니다. 붙인 항목은 건너뛸 수 있고(`POST /practice-sets/:id/items/:itemId/skip`), 단원 통과 기준 계산에서 뺍니다.
- **난이도 상승은 "다음 항목"을 바꾸지 않습니다.** 화면에 이미 떠 있을 수 있는 항목을 바꾸면 학습자가 본 문제가 사라지므로, 그다음 워밍업 항목 중 손대지 않은 것만 바꿉니다. 후보는 세트의 원래 풀에서만 고릅니다.
- **약점 집중 세트의 난이도 사다리는 미리 정합니다.** "정답이면 한 단계씩"은 진행 중 적응의 난이도 상승이 맡습니다.
- **연습한 적 없는 개념은 약점이 아닙니다.** 약점 순위는 `introduced` 이상이면서 시도가 1건 이상 있는 개념만 봅니다. 레슨을 읽자마자 "약점 집중"을 권하지 않기 위해서입니다.
- **복습 큐의 기본 예산은 목표의 복습 몫**(`dailyMinutes × 0.5`, 밀림이 많으면 0.6)입니다. v0.1의 고정 20분을 대체합니다(기본 목표 30분이면 15분). 오늘 공부한 시간으로 줄이지 않아 하루 동안 큐가 안정적이고, 오늘의 학습의 복습 블록만 남은 예산으로 자릅니다.
- **긴 단원은 일부만 계획합니다.** 남은 예산이 5분 이상이면 그만큼 "이어서 학습"·"새 단원"에 배정하고 나머지는 "시간이 남으면"에 둡니다.
- **통과하지 못하고 끝낸 단원은 "이어서 학습"이 아닙니다.** 읽는 중이거나 열린 연습 세트가 있는 단원만 이어서 학습으로 계획하고, 마지막 세트를 통과하지 못한 단원은 다음 단원과 약점 집중으로 넘어갑니다(FR-CUR-05, 학습 잠금 없음). 30일 시뮬레이션에서 한 단원이 매일 예산을 차지해 과정이 멈추는 것을 확인했습니다.
- **복습 세트 후보에 재학습용(`remedial`) 문제를 포함합니다.** 재학습 항목으로만 연습한 선수 개념도 카드가 생기므로, 연습 문제가 없으면 복습할 수 없게 되기 때문입니다.
- **페이스 보정은 보류합니다.** 단원별 실제 소요 시간 기록이 아직 없어 `estimatedMinutes`를 그대로 씁니다. 엔진은 보정 함수를 갖추었고, 학습 세션 기록(`study_sessions`)이 생기면 연결합니다.
- 상세: [학습 엔진 설계 구현 메모 (v0.2)](/docs/design/learning-engine.md#구현-메모-v02), [데이터 모델 설계](/docs/design/data-model.md#remediation_suggestions).

## D-034. 온보딩과 학습 목표 화면 — `확정`
- 2026-11-15, 사용자가 위임한 결정(M5 화면 작업, 권장안대로 진행).
- **온보딩은 대시보드에서만 보냅니다.** `/`를 열 때 `GET /learner`의 `needsOnboarding`이 참이면 `/onboarding`으로 보냅니다. 레슨·설정 같은 직접 주소는 막지 않습니다. 근거: 첫 실행의 기본 진입점은 대시보드이고, 학습 잠금이 없다는 원칙(FR-CUR-05)을 첫 화면에서도 지킵니다.
- **온보딩 완료는 `learners.onboarded_at` 하나로 기록합니다.** "시작" 단계에서 대시보드나 첫 단원으로 나갈 때, 또는 어느 단계에서든 "온보딩 건너뛰기"를 누를 때 기록합니다. 다시 보내지 않습니다. 단계 안의 "건너뛰기"는 그 단계를 저장하지 않고 다음 단계로 갑니다(목표는 기본값 하루 30분·주 5일 유지).
- **v0.1 학습자에게는 묻지 않습니다.** `onboarded_at`이 비어 있어도 학습 기록(단원 진도, 시도, 목표)이 있으면 `needsOnboarding`은 거짓입니다. 마이그레이션으로 값을 채우지 않고 응답에서 판단해, 기록을 바꾸지 않습니다.
- **API**: `GET /learner`, `PATCH /learner` `{ experienceLevel?, onboarded?: true }`. 목표는 기존 `PUT /goals`로 저장합니다. 경험 수준은 지금은 기록만 하고(진단 평가는 P1), "아는 단원은 바로 건너뛸 수 있어요"를 안내합니다.
- **목표 단계의 페이스 미리보기는 브라우저에서 계산합니다.** 목표일을 고르면 그 과정의 단원 예상 시간 합을 목표일까지의 공부일 수로 나눠 "하루 약 N분"을 바로 보여 줍니다(하루 목표보다 많으면 "조금 빠듯해요"). 첫 실행 학습자는 끝낸 단원과 보정값이 없어 서버 계산과 같습니다. 저장한 뒤의 페이스는 서버(`GET /goals`의 `pace`)가 정합니다. 미리보기용 API를 따로 두지 않기 위한 선택입니다.
- **설정 > 학습 목표(`/settings/goals`)를 추가합니다.** 온보딩과 같은 목표 입력을 쓰고, 헤더 GoalRing 팝오버의 "목표 바꾸기"가 이곳으로 옵니다.
- **E2E는 첫 실행 전용 서버를 따로 띄웁니다.** 기존 E2E는 학습자 하나를 공유하므로, 주 서버의 학습자는 시작 전에 온보딩을 마친 상태로 두고(`onboarded.setup.ts`), 온보딩 → 대시보드 상태 → 약점 집중 흐름과 대시보드 시각 회귀는 새 학습자가 있는 두 번째 서버(`E2E_PORT + 1`)에서 고정 시각으로 실행합니다.
- 상세: [UI/UX 설계 온보딩과 목표 설정](/docs/design/ui-ux.md#온보딩과-목표-설정), [시스템 아키텍처 API 규약](/docs/design/system-architecture.md#api-규약).

## D-035. 장기 학습 기억(대화 요약)의 구현 해석 — `확정`
- 2026-11-15, 사용자가 위임한 결정(M5 AI, 권장안대로 진행).
- **요약은 스레드마다 롤링합니다.** 새 요약이 이전 요약을 합쳐 대화 전체를 다루고, `tutor_threads.summary_id`가 최신 요약을 가리킵니다. 튜터 스레드는 단원·문제마다 하나로 계속 이어지므로(M4) "스레드 종료"를 만들지 않고, 30분 비활성마다 그 사이 메시지를 요약에 더합니다. 근거: 스레드를 닫으면 같은 범위의 새 질문이 새 스레드로 갈라져 대화 기록 화면이 바뀌고, 요약 하나로 재구성과 과거 요약 검색을 모두 할 수 있습니다.
- **백그라운드 요약은 Codex가 이미 연결되어 있을 때만** 합니다. 지연 시작 원칙(학습자의 요청이 Codex를 띄움)을 지키고, 사용량 80% 이상·대화형 턴 진행 중에는 미룹니다. 미룬 작업은 `ai_jobs` 큐 없이 DB 상태에서 다시 계산하고, 7일 넘게 밀린 스레드는 결정론적 요약으로 대체합니다(설계의 7일 규칙). `ai_jobs`는 문제 생성처럼 다시 계산할 수 없는 작업이 생길 때 추가합니다.
- **과거 요약은 새 Codex 스레드를 만들 때만** 튜터 맥락에 넣고, 학습 상태(직계 선수 개념 포함)와 활성 오개념은 매 턴 넣습니다. 근거: 이어지는 턴은 Codex 스레드가 과거 요약을 이미 갖고 있고, 학습 상태는 "항상 최신"이어야 합니다.
- **요약의 근거 없는 항목은 재시도하지 않고 지웁니다.** 설계의 "근거 없는 항목은 제거"를 그대로 따르며, 지운 내용은 `ai_calls.validation_issues_json`에 남깁니다.
- `study_session` 요약은 `study_sessions` 기록이 생길 때 구현합니다.
- 상세: [AI 시스템 설계 구현 메모 (v0.2)](/docs/design/ai-system.md#구현-메모-v02), [데이터 모델 설계](/docs/design/data-model.md#tutor_threads-tutor_messages-session_summaries).

## D-036. AI 오답 분석과 오개념 제안의 반영 규칙 — `확정`
- 2026-11-15, 사용자가 위임한 결정(M5 AI, 권장안대로 진행).
- **AI 제안은 의심(`suspected`)만 기록합니다.** 학습 엔진의 `proposeMisconception`이 유일한 반영 경로입니다: 관측이 없으면 새 의심, 기각된 관측은 다시 의심, 이미 의심·확정·해소인 관측은 그대로 둡니다. AI 근거만으로는 확정되지 않고(설계), 해소된 오개념의 재발도 결정론적 근거(오답 선택지·패턴)로만 판정합니다. 근거: 활성 관측에 AI 근거를 더하면 마지막 근거 시각이 갱신되어 30일 기각과 해소 진행이 AI 판단으로 바뀌기 때문입니다.
- **확신도 `low` 제안은 기록하지 않습니다.** 프롬프트가 추측을 `low`로 표시하게 하므로, 기록하면 근거가 약한 미분류 후보가 튜터 맥락에 쌓입니다.
- **오답 분석의 `misconceptionCandidate`도 같은 규칙**(근거 = 그 시도)으로 반영합니다. 학습자가 결과 화면에서 기록 사실을 볼 수 있게 응답에 `misconception`을 돌려줍니다.
- **고른 오답 선택지의 `rationale`은 오답 분석 맥락에 넣습니다.** 채점 후 학습자가 이미 본 피드백이고, 정답 키(다른 선택지의 설명, 정답 선택지)는 넣지 않습니다. 정답 열람 전에는 누설 지문 검사와 코드 8줄 상한을 적용합니다.
- **오답 분석 결과는 저장하지 않고 앱 실행 동안만 시도별로 기억합니다.** 같은 시도를 다시 물어도 사용량을 쓰지 않게 하고, 데이터 모델에 새 테이블을 만들지 않습니다(`ai_calls`에는 매 호출이 남음).
- **오개념 제안 트리거는 장기 기억 백그라운드 점검에서 계산합니다.** 시도 저장 경로(채점 트랜잭션)에 AI 호출을 끼우지 않고, "가장 최근 오답이 분석되었는가"를 `ai_calls`로 판정해 재시작에도 중복 없이 이어 갑니다.
- 상세: [AI 시스템 설계 구현 메모 (v0.2)](/docs/design/ai-system.md#구현-메모-v02).

## D-037. 대시보드와 개념 지도의 데이터 — `확정`
- 2026-11-15, 사용자가 위임한 결정(M5 화면 작업, 권장안대로 진행).
- **`GET /mastery` 하나로 과정 진도와 개념 지도를 줍니다.** 과정마다 완료 단원 수, 단계별 개념 수, 모듈별 개념 타일(단계, 유효 숙련도, 복습 예정 여부, 다음 복습일, 활성 오개념)을 학습 순서(모듈 → 단원 → `lesson.yaml`의 개념 순서)로 담습니다. 개념 수가 과정당 수십~수백 개라 한 번에 보내도 충분히 작고, 과정 진도 카드와 개념 지도가 같은 숫자를 보여 줍니다.
- **진도율은 완료한 단원 비율**이고, 숙련 분포는 따로 숫자로 보여 줍니다(ui-ux.md 과정 진도). 단원 완료는 연습 세트를 통과해야 기록되므로(FR-CUR-05), 통과하지 못한 단원은 진도에 들어가지 않습니다.
- **"복습 예정" 표식**은 FSRS 복습일이 오늘이 지나기 전이거나 인출 가능성이 0.8 아래인 개념입니다. 단계는 시간만으로 내리지 않습니다(학습 엔진 원칙).
- **"약점" 표식(빨간 점)은 확정된 오개념이 있는 개념에만** 붙입니다(ui-ux.md 숙련 단계 스케일). 개념 지도의 "약점만" 보기는 여기에 약점 집중 세트가 고를 개념(`GET /weak-concepts`의 `suggested`)을 더해 보여 줍니다. 약점 순위 상위 10개 전부에 표식을 붙이면, 숙련도가 괜찮은 개념까지 약점으로 보여 학습자를 불필요하게 걱정시키기 때문입니다.
- **약점 집중 세트와 "이 개념만 연습"은 복습 세트 화면(`/review/session/:setId`)에서 진행**하고, 제목을 세트 종류로 바꿉니다("약점 집중"). `/review/weak` 전용 화면은 대시보드의 약점 개념 카드(선택 체크박스, "왜 약점인가요?" 이유 한 줄)로 대신합니다.
- **이번 범위에서 뺀 것**: "최근 활동" 카드(학습 세션 기록 `study_sessions`가 아직 없음), 오늘의 학습에서 이미 끝낸 항목의 체크 표시(`GET /daily-plan`은 남은 항목만 계획함). 둘 다 학습 세션 기록이 생기면 추가합니다.
- 상세: [UI/UX 설계 대시보드](/docs/design/ui-ux.md#대시보드), [시스템 아키텍처 API 규약](/docs/design/system-architecture.md#api-규약).

## D-038. 개념 상세 화면 — `확정`
- 2026-11-15, 사용자가 위임한 결정(M5 화면 작업, 권장안대로 진행).
- **대시보드에서는 오른쪽 시트, 직접 주소(`/concepts/:conceptId`)는 전체 페이지**로 같은 내용을 보여 줍니다(ui-ux.md 사이트맵). 시트는 튜터 드로어와 같은 비모달 Drawer라서 개념 지도를 보면서 다른 타일을 눌러 바꿀 수 있고, `Esc`로 닫으면 연 타일로 포커스가 돌아갑니다. 선수 개념을 누르면 같은 시트에서 그 개념으로 바뀝니다.

- **"이 개념만 연습"은 그 개념 하나로 만든 약점 집중 세트**(`POST /practice-sets {kind:'weakness', conceptIds:[id]}`)입니다. 연습한 적 없는 개념(미학습·근거 없음)에는 버튼을 보이지 않습니다(약점 순위가 연습한 개념만 보는 D-033과 같은 이유).
- 상세: [UI/UX 설계 대시보드 개념 상세 시트](/docs/design/ui-ux.md#대시보드).

## D-039. 실습 모드의 재학습 유도 표시 — `확정`
- 2026-11-15, 사용자가 위임한 결정(M5 화면 작업, 권장안대로 진행).
- **재학습 제안(`remediation`)은 문제 패널 맨 위의 비모달 카드**("잠깐 쉬어가요")로 보여 줍니다. 제안 종류별 버튼(선수 개념 확인하기·풀이 예제 보기·쉬운 문제 풀기·레슨 다시 읽기)과 "계속 풀기"를 같은 무게의 보조 버튼으로 두고, 포커스를 빼앗지 않으며 낭독은 `aria-live="polite"`로 합니다. "왜 이걸 권하나요?"를 펼치면 점검한 선수 개념과 상태가 보입니다. 제안 항목은 이미 세트 끝에 붙어 있으므로(D-033) 버튼은 그 항목으로 이동만 합니다.
- **튜터 배지(`tutorBadge`)는 안내 문장과 배지만** 보여 주고 튜터를 스스로 열지 않습니다(D-010).
- **세트가 바뀌면(`adaptations`) 세트를 다시 받아** 진행 표시에 새 항목을 보여 줍니다. 엔진이 붙인 항목은 진행 표시 점에 점선 테두리와 "(선수 개념 확인)" 같은 이름을, 문제 머리에 배지를 붙입니다. 풀이 예제는 제안에서 받은 단계로 "단계적 풀이 예제 1/3"을 표시합니다(새로 고침하면 단계 번호 대신 "풀이 예제"). 정답 본 뒤의 비슷한 문제, 난이도 상승은 피드백 아래 한 줄로 알립니다.
- **쉬운 문제(`remedial_easier`)의 힌트 1단계는 화면이 엽니다.** 항목을 처음 열 때 `POST /exercises/:id/hints`를 한 번 보내므로, 힌트 기록과 숙련도 가중치는 일반 힌트와 같습니다.
- **"건너뛰기"는 기록합니다.** 지금까지는 다음 문항으로 이동만 했지만, 이제 `POST /practice-sets/:id/items/:itemId/skip`으로 건너뜀을 기록하고(다른 유형의 후속 문항이 끝에 붙음) 다음 미풀이 문항으로 갑니다. 마지막 미풀이 문항을 건너뛰면 세트가 끝나 요약을 보여 줍니다.
- **오개념 변화(`misconceptionChanges`)는 피드백 아래 문장**으로 보여 줍니다: 확인됨("관련 문제를 두 번 맞히면 해소돼요"), "해소 중(1/2)", 해소, 재발, 의심. 기각은 표시하지 않습니다.
- 상세: [UI/UX 설계 재학습 유도](/docs/design/ui-ux.md#재학습-유도), [학습 엔진 설계 재학습 규칙](/docs/design/learning-engine.md#재학습-규칙).


## D-040. v0.2 콘텐츠 범위와 검토 순서 — `확정`
- 2026-11-15, 사용자가 위임한 결정(M5 콘텐츠 작업, 권장안대로 진행).
- **단원 평가 단원은 M6으로 미룹니다.** `html.semantics.review`, `css.layout.review`, JS 각 모듈의 `*-review` 평가 단원은 평가 세트와 평가 맥락 규칙(힌트·튜터 잠금, `W_ctx`, 종료 후 해설)이 생기는 M6에서 함께 만듭니다. 그 전에 만들면 평가 단원이 일반 연습 세트로 동작해 힌트와 튜터를 쓸 수 있어, 평가의 의미가 없어지기 때문입니다. v0.2 `module.yaml`에는 평가 단원을 넣지 않습니다. 모듈 3의 `operators-review`는 커리큘럼상 평가가 아닌 종합 연습 단원이라 그대로 둡니다.
- **초안 작성과 검토를 다른 에이전트가 나눠 합니다(D-027).** 작성 에이전트는 모든 문제를 `draft`로 올리고, 다른 맥락의 검토 에이전트가 모듈 단위로 전수(핵심 단원·핵심 개념) 또는 꼼꼼한 확인(나머지)을 한 뒤 `approved`로 바꿉니다. 검토 기록은 `docs/reviews/`에 남깁니다. `draft` 문제는 배포용 `content.db`에 들어가지 않으므로, 검토가 끝나지 않은 단원은 v0.2에서 레슨만 보이고 연습 문제가 없을 수 있습니다.
- **반응형 단원(`css.layout.responsive`)은 러너가 뷰포트 크기를 바꿔 검사하지 못하면** 개념 확인 유형과 기본 뷰포트에서 검사할 수 있는 실습만 둡니다. 뷰포트별 검사는 이후 러너 기능으로 미룹니다.

## D-041. 단원 평가 단원의 콘텐츠 형식과 문항 선택 — `확정`
- 2026-11-15, 사용자가 위임한 결정(M6 단원 평가, 권장안대로 진행).
- **단원 평가는 모듈 끝의 `kind: assessment` 단원**입니다. 평가할 개념은 `concepts.reviewed`에 두고(`primary`는 비움), 문항은 그 단원의 `usage: assessment` 문제입니다. 선택 필드 `assessment: { itemCount, passRatio }`로 크기(1~20, 생략하면 문항 전부)와 통과 비율(기본 0.8)을 정합니다. `module.yaml`의 `assessment`는 선택이며 생략하면 그 모듈의 평가 단원을 자동으로 연결하고 경고합니다. 이미 쓴 콘텐츠(`operators-review`)를 고치지 않고 받아들이기 위한 하위 호환입니다. `operators-review`는 YAML에 이미 `kind: assessment`와 `usage: assessment` 문항으로 쓰여 있으므로, 이제 평가 세트로 동작합니다(D-040의 "종합 연습 단원으로 그대로 둔다"는 메모를 이 결정이 대신합니다. 커리큘럼 표의 "단원 평가"와도 일치).
- **평가 ID는 평가 단원 ID**입니다. content.db에 `assessments` 테이블을 더하고(스키마 버전 2) 진도는 `lesson_progress`에 그대로 기록합니다. 평가를 단원과 따로 두면 화면·진도·검색이 두 갈래가 되기 때문입니다.
- **평가 문항은 평가에만** 씁니다. 연습·복습·약점 세트 후보에서 빠지고(`usage: practice`만 씀), 일반 단원에 `usage: assessment` 문항을 두면 오류입니다. 평가 문항이 미리 노출되면 "처음 보는 문제"라는 독립 증거의 전제가 깨집니다.
- **문항 선택**: 개념마다 1문항 → 단원 평가 난이도 분포(10/30/35/20/5%)로 나머지 → 쉬운 순서(같은 개념 연속 없음). 모든 선택에서 처음 보는 변형 그룹을 우선하므로 다시 응시하면 풀이 남는 동안 새 문항이 나옵니다. 통과는 `correct` 문항 수 / 전체 ≥ 통과 비율이며 건너뜀은 오답입니다(부분 점수 `partial`은 정답이 아님).
- 학습 엔진 `1.2.0`. 상세: [콘텐츠·문제 시스템 설계 단원 평가 단원](/docs/design/content-and-exercises.md#단원-평가-단원-kind-assessment), [학습 엔진 설계 구현 메모 (v0.3)](/docs/design/learning-engine.md#구현-메모-v03).

## D-042. 평가 맥락 규칙의 서버 적용과 결과 감추기 — `확정`
- 2026-11-15, 사용자가 위임한 결정(M6 단원 평가, 권장안대로 진행).
- **잠금은 서버가 강제합니다.** 평가가 진행 중인 동안 그 문항의 힌트·정답 보기·본문 확인 시도는 `403 EXERCISE_LOCKED_IN_ASSESSMENT`, 튜터·AI 힌트·오답 분석은 `403 AI_LOCKED_IN_ASSESSMENT`입니다. 요청이 연습 항목을 밝히지 않아도 "진행 중인 평가의 문항"이면 잠그고, 평가 단원 스레드의 튜터 질문도 잠급니다. 평가가 끝나면 풀립니다("평가가 끝나면 열려요"). 화면만 막으면 API를 직접 불러 우회할 수 있기 때문입니다.
- **결과는 끝날 때까지 응답에 싣지 않습니다.** 평가 중 시도 응답은 정오·피드백·해설·숙련도 변화가 없는 `withheld` 형태이고, 세트 조회의 `lastOutcome`은 `null`, 개념 상세의 문항별 근거는 숨깁니다. 마지막 제출이 문항별 결과·해설·정답·틀린 개념을 한꺼번에 돌려줍니다. 숙련도·FSRS 반영을 종료 시점으로 미루지 않은 것은 시도 순서에 의존하는 규칙(`W_rep`, 오개념 전이, 하루 한 번 평가)을 다른 세트와 같은 경로로 처리하기 위해서이며, 그 결과 평가 중에도 개념 점수 합계는 바뀔 수 있습니다(문항별 정오는 드러나지 않음).
- **문항마다 한 번만 제출**(`409 PRACTICE_ITEM_DONE`), 건너뛰기는 허용하되 오답으로 셉니다. 통과하면 평가 단원을 완료로 기록하고, 통과하지 못해도 다음 단원을 막지 않습니다. 재응시는 새 세트이며 처음 보는 문항을 우선합니다(D-041).
- **약점 집중 제안**은 틀리거나 건너뛴 문항의 주 개념 중 앞의 5개입니다(약점 집중 요청의 최대 개수).
- 상세: [학습 엔진 설계 구현 메모 (v0.3)](/docs/design/learning-engine.md#구현-메모-v03), [시스템 아키텍처 API 규약](/docs/design/system-architecture.md#api-규약).

## D-043. 단원 평가 화면 — `확정`
- 2026-11-15, 사용자가 위임한 결정(M6 단원 평가, 권장안대로 진행).
- **시작 화면을 거쳐야 평가가 시작됩니다.** 규칙(힌트·튜터·정답 보기 없음, 문항당 한 번 제출, 끝난 뒤 정답·해설, 확신도는 솔직하게, 건너뜀은 오답)과 문항 수·개념 수·통과 기준·예상 시간을 먼저 보여 주고 "평가 시작"으로 세트를 만듭니다. 잠금이 있는 화면에 갑자기 들어가 당황하지 않게 하기 위함입니다.
- **평가 중에는 튜터를 화면에 두지 않고, 버튼만 잠긴 상태로 보여 줍니다.** 드로어·`⌘J`·선택해서 질문하기를 모두 빼고 헤더 버튼을 `aria-disabled` + "평가가 끝나면 열려요"로 둡니다(ui-ux.md 피드백 타이밍). 서버도 잠그지만(D-042) 열리지 않을 기능을 열어 두면 오류만 보게 되기 때문입니다. 힌트 사다리는 기존 `locked` 상태를 씁니다.
- **문항 화면은 연습과 같은 레이아웃**을 쓰되 정오·해설·숙련도 변화·개념 이름·"다시 풀기"를 감추고, 제출하면 "제출했어요" 안내와 "다음 문제"를 보여 줍니다. 자동으로 넘기지 않아 학습자가 흐름을 정합니다. 진행 표시는 정오 색 대신 회색 "제출함" 점입니다.
- **종료 화면은 결과 → 이유 → 다음 행동** 순서입니다: 점수와 통과 여부, 개념별 결과, 틀린 개념의 약점 집중, 문항별 정답과 해설(틀린 문항은 펼침), 다시 응시·다음 단원.
- 상세: [UI/UX 설계 단원 평가 화면](/docs/design/ui-ux.md#단원-평가-화면).

## D-044. 오답 노트·숙련도 변화의 데이터와 "다시 풀기" — `확정`
- 2026-11-15, 사용자가 위임한 결정(M6 복습 화면, 권장안대로 진행).
- **저장하지 않고 파생합니다.** 오답 노트는 시도에서(용어집 `MistakeNote`), 숙련도 변화는 이미 업데이트마다 `stage_before`·`stage_after`를 남기는 `mastery_evidence`에서 만듭니다. 별도 이력 테이블을 두면 같은 사실을 두 곳에 적게 되고, 백업 복원·재계산 때 어긋날 수 있습니다. 마이그레이션은 없습니다.
- **노트는 문제마다 하나**이고 마지막 오답(`incorrect`·`partial`)을 대표로 보여 줍니다. 마지막 오답 뒤에 **정답을 보지 않고** 같은 문제를 맞히면 `resolved`, 다시 틀리면 `open`으로 돌아갑니다. 학습자가 직접 "해결" 표시를 하는 기능은 두지 않습니다. 실제로 다시 맞혔는지가 기준이어야 노트가 믿을 만하기 때문입니다. 정답을 본 뒤 맞힌 것은 따라 쓴 것일 수 있어 해결로 보지 않습니다.
- **보여 주는 것은 학습자가 이미 본 것뿐**입니다. 내 답, 그때의 피드백 문장, 오개념 이름, 해설(채점 때마다 보여 줌)은 항상 보이고, 정답은 "정답 보기"로 연 적이 있거나 끝난 단원 평가의 결과 화면이 보여 준 경우에만 보입니다. 평가 문항은 문항별 피드백을 보여 준 적이 없으므로 피드백을 빼고, **진행 중인 평가의 시도와 그 문항의 이전 노트, 숙련 단계 변화는 평가가 끝날 때까지 숨깁니다**(D-042).
- **"다시 풀기"는 그 문제 하나(또는 고른 최대 10개)로 만든 `extra` 세트**입니다. 연습 세트 밖의 본문 확인 시도(`inline-attempts`)는 실행이 필요한 유형을 받지 못하고 힌트 사다리·재학습·FSRS 일정도 없으므로, 세트 화면을 그대로 쓰는 쪽이 모든 유형에서 같은 경험을 줍니다. 평가 전용 문항은 다시 풀 수 없고(재응시의 "처음 보는 문항" 전제), 대신 같은 개념의 약점 집중 세트("비슷한 문제 풀기")를 권합니다.
- **숙련도 변화의 주별 요약은 월요일 시작 주**(학습자의 하루 시작 시각 기준, 주간 목표와 같은 주)로 최근 8주를 빈 주까지 채워 돌려줍니다.
- 상세: [학습 엔진 설계 구현 메모 (v0.3)](/docs/design/learning-engine.md#구현-메모-v03), [데이터 모델 주요 쿼리 경로](/docs/design/data-model.md#주요-쿼리-경로), [시스템 아키텍처 API 규약](/docs/design/system-architecture.md#api-규약).

## D-045. 설정 > 데이터: 백업 위치 변경, 복원 전 검사, 학습 데이터 초기화 — `확정`

- **복원 대화상자는 서버 검사 결과를 먼저 보여 줍니다**(`GET /backups/:id/check`). 손상·새 버전 백업은 확인 버튼을 누르기 전에 알 수 있어야 하고, 이전 버전 백업은 복원 후 마이그레이션이 돈다는 것을 알려 줍니다. 복원·초기화는 유지보수 모드 진입 직후 진행 중인 튜터 턴을 취소합니다.
- **초기화는 남길 테이블만 정하고 나머지를 모두 지웁니다.** 남기는 것: 마이그레이션 이력, `app_meta`, 학습자 행(시간대·하루 경계), `settings`(화면·학습 방식), 백업, AI 연결. 지우는 것: 진도·시도·힌트·숙련도·FSRS·오개념·튜터 대화와 요약·AI 호출 기록·목표·학습 시간. 허용 목록이 아니라 제외 목록이라 이후 추가되는 학습 테이블이 초기화에서 빠지는 실수가 없습니다. 목표와 경험 수준도 지우므로 온보딩을 다시 보여 줍니다("처음부터 다시"의 자연스러운 시작점). 설정을 남기는 이유는 초기화가 "학습 기록"을 지우는 기능이지 앱 설정을 되돌리는 기능이 아니기 때문입니다.
- **확인은 입력란 + 서버 재확인입니다.** "초기화"를 정확히 입력해야 버튼이 켜지고, 서버도 본문 `{ confirm: "초기화" }`가 없으면 거부합니다(실수로 보낸 요청 방지). 되돌리기는 "초기화 전" 백업 복원입니다.
- 상세: [데이터 모델 설계 학습 데이터 초기화](/docs/design/data-model.md#학습-데이터-초기화), [백업 위치 변경](/docs/design/data-model.md#백업-위치-변경), [UI/UX 설계 설정](/docs/design/ui-ux.md#설정).

## D-048. 응용 프로젝트 단원의 콘텐츠 형식, 진도와 숙련도 반영 — `확정`
- 2026-11-15, 사용자가 위임한 결정(M6 응용 프로젝트, 권장안대로 진행).
- **프로젝트는 `kind: project` 단원 + `usage: project` 웹 실습 하나**입니다. 단계는 `web_task`의 `milestones`이고, 별도 `projects` 테이블·`steps_json`은 만들지 않습니다(content.db는 `exercises.usage`에 `project`를 더해 스키마 버전 3, `modules.project_id`에 모듈의 프로젝트 단원). 단원은 새 개념을 소개하지 않고(`primary` 비움) 적용할 개념을 `practiced`·`reviewed`에 둡니다. 설계 문서의 "최종 프로젝트도 `web_task` 마일스톤으로 구현" 방침을 그대로 따르고, 이미 있는 채점·마일스톤 결과·체크 목록 UI를 다시 쓰기 위해서입니다. `usage: project`라서 연습·복습·약점 세트 후보에 섞이지 않습니다.
- **준비 연습은 그 단원 안에서만.** 프로젝트 문제 외의 문제(`usage: practice`)는 단원의 준비 연습이며, 그 단원의 연습 세트(`practiced` 개념별, 그 단원 문제만, 통과 기준 없음)에만 나오고 다른 단원·복습·약점·재학습 세트 후보에서는 빠집니다. 준비 연습은 앞 단원에서 배운 개념을 프로젝트 맥락으로 묶은 문제라, 다른 단원(특히 아직 그 개념을 배우기 전)에 섞이면 맥락이 깨지기 때문입니다. 프로젝트 문제를 `usage: project`로 표시하지 않으면 단원의 유일한 마일스톤 `web_task`를 프로젝트 문제로 쓰고 경고합니다(모듈 10 콘텐츠를 고치지 않고 받기 위한 하위 호환, D-041과 같은 방식).
- **프로젝트 문제는 연습 세트에 넣지 않습니다.** 프로젝트 화면이 `GET /lessons/:id/project`와 `POST /lessons/:id/project/attempts`로 직접 채점하고, 시도는 `practice_set_item_id` NULL로 기록합니다. 프로젝트 단원에 세트를 요청하면 `409 PRACTICE_KIND_MISMATCH`입니다. 새 세트 종류(`practice_sets.kind = 'project'`)를 쓰려면 SQLite `CHECK` 변경 때문에 `practice_sets` 테이블을 다시 만들어야 하는데, 마이그레이션 안에서 외래 키 연쇄 삭제(`practice_set_items`)를 막을 수 없어 기록 손실 위험이 있습니다. 세트의 적응·통과 기준·건너뛰기도 프로젝트에는 맞지 않습니다.
- **숙련도는 모든 마일스톤을 처음 통과한 채점 한 번만 반영**합니다. 중간 채점은 아직 만들지 않은 단계가 실패로 나오는 것이 정상이므로 오답 증거로 쓰면 적용 개념의 숙련도가 부당하게 떨어지고, 완료 뒤의 채점은 같은 일의 반복입니다. 반영하지 않은 채점은 `engine_applied = 0`으로 남겨 엔진 반영 시도 집계와 오답 노트에서 빠지고(D-044의 오답 노트도 이제 `engine_applied = 0` 시도를 넣지 않음), 프로젝트 문제는 "다시 풀기" 세트에 담을 수 없습니다. 완료 채점은 첫 시도(`W_try` 1.0)로 보고, 힌트·정답 보기·튜터 가중치는 그대로, 학습 맥락이라 `W_ctx` 1.0, FSRS 등급은 만들지 않습니다. 힌트·정답 보기 없이 끝낸 L4 이상 프로젝트는 일반 규칙대로 `mastered` 게이트의 독립 응용 증거가 됩니다.
- **완료는 모든 마일스톤 통과**이며 한 번 완료하면 유지합니다. 진행 표시는 마지막 채점 결과(앞 단계가 실패한 뒤의 `event` 체크 마일스톤은 "앞 단계 먼저"), 이어 하기는 마지막 제출 코드(화면에서는 더 최근의 브라우저 초안 우선)입니다. 해설은 완성한 뒤에만 응답에 싣습니다.
- **계획**: 페이스(목표일 계산)에는 넣지 않고(설계대로), 오늘의 학습에서는 진행 중인 프로젝트를 "이어서 학습"(남은 시간 = 연습 예상 × 남은 마일스톤 비율), 아직 시작하지 않은 프로젝트를 과정 순서상의 "새 단원" 후보로 둡니다. 과정 진도의 단원 수·완료 수에는 셉니다.
- 상세: [콘텐츠·문제 시스템 설계 프로젝트 단원](/docs/design/content-and-exercises.md#프로젝트-단원-kind-project), [학습 엔진 설계 구현 메모 (v0.3)](/docs/design/learning-engine.md#구현-메모-v03).

  - Mermaid는 글자 크기를 실제 브라우저 레이아웃으로 재므로 `content:build`마다 헤드리스 브라우저가 필요하고, 학습자 기기의 글꼴과 다르게 잴 수 있습니다.

- **빌드 검사**: `content:check`가 자식 프로세스(jsdom + Mermaid 파서)로 모든 다이어그램의 구문을 검사해 오류를 빌드 오류로 냅니다. 지시문, front matter 설정, `click`·`link` 상호작용은 쓸 수 없습니다. 런타임에 그리지 못하면 안내 문구, `alt`, 펼친 소스를 보여 줍니다.
- **접근성**: 그림은 `role="img"` + `alt`, 소스는 접힌 텍스트 대안. `caption`(선택) 속성을 더합니다.
- 의존성: `mermaid`, `dompurify`(웹), `mermaid`, `jsdom`(content-cli). 상세: [콘텐츠·문제 설계 MDX 컴포넌트](/docs/design/content-and-exercises.md#mdx-컴포넌트).

## D-052. 단원 선수 개념 경고와 숙련도 — `확정`
- 2026-11-15, 사용자가 위임한 결정(M6 P0 점검 must-fix 4, FR-CUR-05·FR-CUR-02).
- **"약하다"는 학습 엔진 재학습 규칙과 같은 기준입니다**: 유효 숙련도 60 미만 또는 `practicing` 미만(`assessPrerequisite`, `config.remediation.weakPrerequisiteBelow`). 단원 경고만을 위한 다른 문턱을 두면 같은 개념이 단원 화면에서는 괜찮고 실습에서는 "선수 개념부터"가 되는 모순이 생깁니다. 아직 배우지 않은 개념(`not_started`)도 약함입니다. 권장 순서대로 앞 단원을 연습한 학습자는 대개 `practicing`에 닿아 경고가 사라지고, 순서를 건너뛴 학습자에게만 남습니다.
- **경고 대상은 단원이 소개하는 개념(`primary`)의 직계 `required` 선수 개념**이며, 그 단원이 소개하는 개념은 뺍니다. 재학습은 깊이 2까지 보지만, 단원을 열 때는 직계만 봅니다: 깊이 2까지 보면 초반 개념 하나가 약할 때 뒤 단원마다 경고가 떠 경고가 소음이 됩니다. `helpful` 선수 개념과 `lesson.yaml`의 `reviewed` 개념은 "선수 개념 확인" 섹션에 숙련도와 함께 보이지만 경고하지 않습니다. 평가·프로젝트 단원은 새 개념을 소개하지 않아 경고가 없습니다(평가는 측정 자체가 목적이고, 프로젝트 화면은 준비 연습 카드가 같은 역할).
- **경고는 막지 않는 안내 상자이고 닫기 버튼이 없습니다**(ui-ux.md 학습 화면: 읽기 모드). 링크는 개념 상세, 그 개념을 소개하는 단원(`introduced_in_lesson_id`), 약점 연습입니다. 약점 연습은 한 번이라도 문제를 푼 개념에만 보입니다: 약점 집중 세트는 풀어 본 개념만 약점으로 보므로(읽기만 한 개념은 "아직 연습 전", learning-engine.md#약점-집중-세트), 그 밖의 개념에 버튼을 두면 누를 때마다 `PRACTICE_NOTHING_WEAK`로 실패합니다. 이때는 앞 단원 링크가 올바른 다음 행동입니다.
- **API는 `GET /lessons/:id`에 넣지 않고 `GET /lessons/:id/prerequisites`로 나눕니다.** 단원 상세는 content.db만 담아 웹이 `staleTime: Infinity`로 캐시하는데(앱 재시작 전에는 바뀌지 않음), 숙련도는 연습할 때마다 바뀝니다. 한 응답에 섞으면 단원 본문까지 매번 다시 받거나 숙련도가 낡습니다. 숙련도 요청이 실패해도 단원은 그대로 열리고 경고·숙련도만 빠집니다.

## D-053. 채점에서 취소되지 않은 폼 제출은 즉시, 매번 같은 오류 — `확정`
- 2026-11-15, 사용자가 위임한 결정(M6 P0 점검 must-fix, 모듈 10 검토의 후속 과제).
- **문제**: 채점(`dom` 모드)에서 `preventDefault()`를 빠뜨린 폼 제출은 셸 CSP가 막고 문서가 오류 페이지로 바뀌어 `pagehide`로 `NavigationError`가 되는데, 이동은 다음 작업에서 일어나므로 남은 관측 단계가 먼저 끝나면 통과했습니다. 같은 답이 실행마다 통과·실패했습니다(채점 결정론 위반).
- **선택: 하네스가 제출 직후 동기적으로 판정하고 실행을 끝냅니다.** 학습자 코드보다 먼저 단 캡처 단계 `submit` 리스너가 신뢰된 제출마다 마이크로태스크를 예약하고, 마이크로태스크(모든 학습자 핸들러 뒤, 이동 작업 앞)가 미리 잡은 `defaultPrevented` getter로 취소 여부를 읽습니다. 취소되지 않았고 문서를 떠나는 제출이면 `NavigationError`를 기록하고 남은 단계 없이 끝냅니다. 그래서 실행 상태·관측 목록·채점 결과가 매번 같습니다.
- 버린 안: (1) 이동을 끝까지 기다린 뒤 판정 — Chromium 외 엔진은 막힌 이동에서 `pagehide`가 없어(code-execution-sandbox.md의 Firefox·WebKit 로컬 참고 실행) 결국 실행 시간 제한까지 기다리게 되고, 기다리는 시간도 정할 근거가 없습니다. (2) 채점에서도 미리보기처럼 제출을 가로채 취소 — 실제 브라우저와 다르게 `preventDefault()` 누락이 통과하므로 이 개념을 채점할 수 없습니다. (3) 오류만 기록하고 단계를 계속 실행 — 실행 결과는 늘 `error`가 되지만, 체크 목록의 통과·실패가 여전히 시점에 따라 달라집니다.
- 샌드박스 플래그·CSP는 바꾸지 않습니다(전송은 여전히 `form-action 'none'`이 막음). 오류 문구는 기존 문장 뒤에 "submit 이벤트 처리기에서 event.preventDefault()로 폼 전송을 막았는지 확인하세요."를 덧붙여, 레슨이 인용한 문장과 맞으면서 고칠 곳을 알려 줍니다.
- **최종 프로젝트 시작 코드에 `preventDefault()`만 있는 빈 `submit` 함수를 둡니다.** 판정이 결정론적이 되면서, 시작 코드를 그대로 채점하면 매번 "코드를 끝까지 실행하지 못했어요"와 `NavigationError`만 보이고 마일스톤 진행은 보이지 않습니다. 기본 동작 막기는 같은 모듈의 이벤트 단원·준비 연습(객관식·파슨스)에서 이미 연습하고, 프로젝트의 목적은 여러 기능을 단계별로 조립하는 것이라 뼈대를 주는 편이 낫다고 판단했습니다. 지문의 1단계와 힌트 1단계도 맞게 고쳤습니다. 이 문제는 `usage: project`로 표시해 content-cli 경고(D-048 하위 호환)를 없앱니다.
- 콘텐츠의 "실패할 수 있어요"·"통과할 때도 있지만" 문장은 "매번 실패해요"로 고칩니다(이벤트 단원 레슨, `web-signup-form` 해설). 상세: [코드 실행 샌드박스 실행 동작](/docs/design/code-execution-sandbox.md#실행-동작), 보안 스위트 S49.

## D-057. 콘텐츠 별칭(FR-CUR-06): `aliases.yaml`, 공개 slug 목록, user.db 일괄 갱신 — `확정`
- 2026-11-16, 사용자가 위임한 결정(M7 작업 "콘텐츠 별칭", M6 P0 점검 M7 목록 10).
- **원본 형식**: `content/aliases.yaml`은 `{ from, to, kind: rename|merge|split, since?, primary? }`의 목록입니다(설계 예시와 같음). `rename`·`merge`의 `to`는 slug 하나, `split`은 2개 이상이고 진도를 이어받을 `primary`가 필요합니다. `merge`는 합쳐진 이전 slug마다 한 항목씩 씁니다. `since`를 생략하면 빌드하는 팩 버전입니다. 대상 종류(`entity_kind`)는 쓰지 않고 `to`가 현재 콘텐츠에서 무엇인지(과정·모듈·단원·개념·오개념·문제)로 정합니다.
- **검사**: `from`이 아직 콘텐츠에 있으면, `to`가 없으면, `to`의 종류가 섞이면, `from`이 대상 종류의 slug 형식이 아니면, 같은 `from`이 두 번이면 오류입니다. 별칭 사슬(A→B, B→C)은 `to`가 현재 slug여야 하므로 생기지 않습니다(이전 별칭은 최종 slug로 고칩니다). 아직 공개되지 않는 대상(미검토 문제, 소개되지 않은 개념)과 항목이 하나뿐인 `merge`는 경고입니다. 빌드는 행을 `content_id_aliases`에 씁니다(split은 대상마다 한 행, `is_primary`).
- **사라진 slug 비교는 커밋하는 목록 파일로 합니다**: `content/.published-slugs.txt`(설계 문서의 이름). `content/dist/content.db`와 비교하는 안은 버렸습니다: `dist/`는 저장소에 없어서 CI와 새로 받은 작업 사본에서는 비교할 대상이 없고, 개발용 `--include-drafts` 빌드가 덮어쓰면 기준이 흔들립니다. 목록은 `<종류> <slug>` 줄로 된 정렬된 텍스트라 PR diff에서 무엇이 사라졌는지 바로 보입니다. `content-cli build`(초안 제외 빌드)가 갱신하고, `check`는 목록에 있던 slug가 콘텐츠에서 사라졌는데 별칭이 없으면 **경고**합니다(승인됐던 문제가 초안으로 돌아간 경우도). 의도한 삭제는 `pnpm content:build`로 목록을 갱신해 커밋하면 경고가 사라집니다. 설계는 이 경우를 오류로 적었지만, v1.0 전까지는 미공개 초안 정리와 단원 재구성이 잦아 경고로 시작합니다(삭제를 확인하는 단계가 목록 커밋 diff 리뷰입니다). 목록 파일이 없으면 비교하지 않습니다. 첫 목록(현재 콘텐츠의 공개 slug 1,606개)은 이 결정과 함께 커밋해 처음부터 비교가 켜져 있습니다.
- **서버는 읽을 때마다 해석하지 않고, 시작할 때와 백업 복원 뒤 user.db를 한 번 갱신합니다**(data-model.md#콘텐츠-참조와-고아-처리의 "갱신"). user.db의 콘텐츠 참조 열(시도·힌트·세트 항목·스냅샷·신고의 문제 ID와 변형 그룹 키, 숙련도·증거·기억·복습 기록·대기 평정·요약 개념·오개념 관찰·재학습 제안의 개념 ID, 단원 진도, 목표 과정, 튜터 스레드·요약 범위, AI 호출 대상)을 이전 slug → 현재 slug로 한 트랜잭션에서 바꿉니다. 그 뒤 모든 읽기(시도, 숙련도, 기억, 오답 노트, 진도)가 현재 slug를 봅니다. 읽기 시점 해석은 서비스마다 수십 개 쿼리를 고쳐야 하고 빠뜨리면 같은 개념이 두 개로 보이므로 버렸습니다. 바꿀 행이 있을 때만 먼저 `pre-migration` 백업을 만들고, 적용한 별칭 집합의 지문을 `app_meta`(`content_aliases_applied`)에 남겨 다음 시작부터 건너뜁니다. 별칭이 생기기 전 백업을 복원하면 지문이 달라 다시 적용합니다. 적용이 실패하면 기록을 그대로 두고 로그만 남깁니다(그 기록은 기존처럼 보관된 콘텐츠로 보임).
- **split은 `primary` 대상으로 옮깁니다. 키가 겹치는 행은 옮기지 않습니다**: 학습자·개념(또는 단원)마다 한 행인 숙련도·기억·진도는 새 slug에 행이 없을 때만 옮기고(`UPDATE OR IGNORE`), 이미 있으면 이전 행을 지우지 않고 남깁니다(고아, 화면에서 빠짐). merge된 개념의 숙련도·기억을 근거 시도에서 다시 계산하는 일(설계의 "재계산")과 split 개념의 시도 재배분은 서버에 시도 재생 경로가 없어 후속 작업으로 둡니다. 시도·증거 같은 이력 행은 모두 옮기므로 재계산에 필요한 근거는 보존됩니다. JSON 안의 slug(시도의 오개념 목록, 세트 범위, 요약 개념 목록)는 당시 스냅샷으로 보고 바꾸지 않습니다.

## D-058. 템플릿 변형은 빌드 때 실행 검증한 시드 풀에서만 출제 — `확정`
- 2026-11-16, 사용자가 위임한 결정(M7 P0 점검 항목 2, FR-EX-08·FR-EX-14).
- **문제**: 설계는 변형을 처음 출제할 때 웹 앱이 숨김 검증 실행으로 기대값을 계산해 서버에 보고하고, 서버가 `user.db`의 `variant_cache`에 캐시하는 방식이었습니다. 러너는 브라우저에만 있어 서버가 직접 실행할 수 없고, 이 방식은 (1) 출제 전에 한 번 더 왕복과 실행이 필요하며, (2) 정답 키를 클라이언트가 만들어 보고하므로 "정답은 서버가 갖고, 클라이언트는 관측만 한다"는 채점 원칙([채점 위치와 정답 키 비노출](/docs/design/content-and-exercises.md#채점-위치와-정답-키-비노출))과 어긋나고, (3) 보고된 값이 틀렸을 때 검증할 기준이 없습니다.
- **선택: 빌드 때 실행 검증한 표본 시드만 출제합니다.** `content-cli check --run`이 템플릿마다 `sampleSeeds(id, n)`(기본 50, `variantPolicy.sampleSize`, 5~100)로 변형을 만들고, 렌더링 결과가 같은 표본은 하나로 합친 뒤, 각 변형을 저작 문제와 똑같이 앱의 러너에서 실행 검증합니다(`predict_output`은 3번 실행해 결정론 확인 후 정답 키 계산). 통과한 변형만 `content/.generated/template-expected.json`에 변형 ID(`<템플릿 ID>@<시드>`)와 입력 해시로 기록하고(정답 키가 없는 유형은 `expected: null`), `content:build`가 그 변형들을 `template_variants`에 시드 풀로 저장합니다. 서버는 이 풀의 시드만 `exercise-kit` 엔진으로 즉석에서 만들어 내고(결정론적), 정답 키는 풀에 저장된 실행 결과를 씁니다. 풀 밖의 시드는 실행된 적이 없으므로 404입니다.
- 결과: 모든 변형의 정답은 실제 실행 결과이고(저자도 표현식 언어도 정답을 쓰지 않음), 런타임에 숨김 실행·`variant_cache`·클라이언트 보고 API가 필요 없습니다. 같은 원본은 항상 같은 content.db가 되고, 빌드에는 브라우저가 필요 없습니다(예측 문제 기대값 파일과 같은 방식).
- 비용: 변형 수가 템플릿당 표본 수(최대 100)로 제한됩니다. 학습자 한 명이 한 템플릿의 변형 50개를 다 보는 일은 드물고, 다 보면 가장 오래전에 본 변형부터 다시 냅니다(D-059). 더 필요하면 `sampleSize`를 늘립니다. CI의 `content:check:run --frozen` 시간이 표본 수만큼 늘어납니다(초안 템플릿 3개 × 30개 = 변형 90개로 약 3초).
- 검사 규칙: 표본 하나라도 만들 수 없으면(제약 불만족, 스펙 오류) 오류, 서로 다른 변형이 5개 미만이면 오류, `misconceptionByAnswer`의 오답이 어떤 변형의 실제 정답과 같으면 오류(`PREDICT_MISCONCEPTION_EQUALS_ANSWER`), 정답의 80% 이상이 같으면 경고, 승인된 템플릿에 실행 검증 기록이 없거나 낡으면 오류(초안은 경고, 빌드에서 그 변형 제외). 템플릿은 JavaScript 과정에서만, `web_task`를 뺀 유형으로 만듭니다. 템플릿 원본에 `spec.expected`를 쓰면 오류입니다.
- 템플릿 파일은 `lessons/<단원>/templates/*.yaml`이고, 초안·승인 규칙(`review`)은 문제와 같습니다([D-027](/docs/decisions.md)). content.db 스키마 버전이 4가 되었습니다(`exercise_templates`, `template_variants`).
- 상세: [콘텐츠·문제 시스템 설계 구현 메모 (M7)](/docs/design/content-and-exercises.md#정답의-실행-계산), [콘텐츠 작성 가이드 파라메트릭 템플릿](/docs/guides/content-authoring.md#파라메트릭-템플릿).

## D-059. 템플릿 변형 선택: 템플릿마다 안 본 변형 하나, 반복보다 새 변형 — `확정`
- 2026-11-16, 사용자가 위임한 결정(M7 P0 점검 항목 2, FR-EX-08·FR-EX-14, PRD 흐름 5 "더 풀고 싶을 때", [D-009](/docs/decisions.md)의 "복습 시에는 같은 문제가 아닌 새 변형").
- **후보에 넣는 곳**: 단원 연습 세트(첫 세트와 "한 번 더 연습"으로 만드는 다음 세트, 그 단원의 템플릿과 복습 개념의 템플릿), 복습 세트와 약점 연습(대상 개념의 `practice`·`remedial` 템플릿), 진행 중 적응(정답 열람 후 후속 문항 등, 대상 개념의 템플릿). 단원 평가와 오답 노트 "다시 풀기"에는 넣지 않습니다(평가는 정해진 문항, 다시 풀기는 틀린 그 변형을 그대로 다시 냄).
- **템플릿마다 후보는 변형 하나**입니다. 엔진은 한 세트에 변형 그룹당 하나만 넣으므로(템플릿 ID가 그룹 키) 여러 개를 넘길 이유가 없습니다. 고르는 규칙: 시드 풀(D-058)을 세트 ID로 시드한 순서로 섞고, (1) 학습자가 아직 받은 적 없고 정답이 최근 `minDistinctFromRecent`개(기본 3) 변형과 다른 것, (2) 없으면 아직 받은 적 없는 것, (3) 풀을 다 받았으면 가장 오래전에 받은 것. "받은 적"은 `practice_set_items`에 담긴 적이 있는지입니다(답하지 않고 넘긴 것도 포함). 같은 세트는 다시 만들어도 같은 변형이고, 세트가 다르면 대개 다른 변형입니다.
- **반복보다 새 변형**: 엔진의 후보 선택(`pickBest`)은 지금까지 "신선도 > 난이도 범위 > 점수" 순이었는데, 신선도는 변형 그룹 기준이라 10일 전에 푼 문제은행 문제와 10일 전에 본 템플릿의 새 변형이 같은 단계였고, 점수의 `originPreference`(`authored` 1.0, `template` 0.8) 때문에 같은 문제의 반복이 이겼습니다. `SelectionContext.seenExerciseIds`(학습자가 답한 적 있는 문제 ID, 변형은 시드까지 포함한 ID)를 더해, 같은 신선도·같은 범위 안에서는 아직 답하지 않은 문제가 반복보다 먼저 오게 했습니다. 신선도가 먼저라서 7일 안에 본 템플릿의 새 변형은 여전히 신선한 다른 문제보다 뒤입니다(증거 가중치 `W_rep`와 같은 판단). 서버는 단원·복습·약점 세트와 적응 단계에 이 값을 넘기고, 넘기지 않으면 예전과 같습니다.
- **신고**: 변형 하나를 "문제 신고"하면 그 템플릿 전체를 더는 출제하지 않습니다. 변형의 문제는 거의 항상 템플릿에서 오기 때문입니다. 신고 안내 문구("이 문제는 다시 나오지 않아요")는 그대로 둡니다.
- 시도 기록: `attempts.exercise_id`는 변형 ID(`<템플릿 ID>@<시드>`), `exercise_origin`은 `template`, `variant_group_key`는 템플릿 ID(또는 템플릿의 `variantGroup`)입니다. 그래서 같은 템플릿의 반복 정답은 `W_rep`로 감쇠되고(FR-EX-14), 과거 풀이는 같은 변형으로 다시 만들 수 있습니다.
- 웹은 바꾸지 않았습니다. 변형은 일반 문제와 똑같이 보이고(ui-ux.md에 변형 전용 화면이 없음), 문제 ID에 `@`가 들어가도 기존 API 경로가 그대로 동작합니다.
- 상세: [학습 엔진 설계 구현 메모 (M7)](/docs/design/learning-engine.md#문제-후보와-점수).

## D-060. AI 모델 선택: 저장은 `settings.ai.model`, 실행마다 목록과 맞춰 없으면 기본 모델 — `확정`
- 2026-11-16, 사용자가 위임한 결정(M7 작업, FR-SET-01, P0 점검 M7 5번).
- **저장 값**: 학습자가 고른 모델 ID를 `settings.ai.model`에 저장합니다. `null`이 기본값이고 "Codex가 정한 기본 모델(`isDefault`)을 따른다"는 뜻입니다. 설정 화면에서 기본 모델을 고르면 그 ID가 아니라 `null`을 저장해, 제공자의 기본 모델이 바뀌면 학습자도 따라가게 합니다. `null`을 저장하면 행을 지워 기본값으로 돌아갑니다(새 키라 마이그레이션 없음).
- **적용 위치는 작업 실행기(`TaskRunner`) 하나입니다.** 서버가 `resolveModel`을 주입하면 실행기가 턴 슬롯을 얻은 뒤 모델을 정해 `thread/start`·`thread/resume`의 `model`로 보냅니다(공식 App Server 프로토콜 필드, 비공식 엔드포인트 없음). 다섯 AI 작업(튜터 답변·힌트, 오답 분석, 세션 요약, 오개념 제안)이 모두 같은 규칙을 따르고, 작업마다 호출부를 고치지 않습니다. `ai_calls`에는 실제로 쓴 모델과 추론 강도가 남습니다.
- **저장한 모델이 `model/list`에서 사라지면 기본 모델로 실행하되 저장 값은 지우지 않습니다.** ai-system.md는 "기본 모델로 되돌리고 알림"이라고 적었는데, 목록이 잠시 비거나 플랜이 바뀌는 동안 값을 지우면 모델이 다시 보여도 학습자의 선택이 사라집니다. 그래서 실행 시점에 기본 모델로 대체하고(작업은 실패하지 않음), 설정 > AI가 "저장한 모델(…)을 더 이상 쓸 수 없어서 기본 모델(…)로 답해요"를 경고 상자로 알립니다. 다른 모델을 고르면 바뀝니다. 같은 판정 함수(`pickModel`, `@proginone/shared`)를 서버와 화면이 함께 씁니다.
- **모델 목록은 10분 캐시합니다.** 실행마다 `model/list`를 부르면 대화형 응답에 왕복 하나가 더 붙습니다. 설정 화면이 목록을 받을 때(`GET /ai/models`)와 로그아웃·다시 연결 때 캐시를 갱신·삭제하므로 학습자가 보는 목록과 실행이 어긋나는 시간은 짧습니다. 목록을 못 받으면 `model`을 보내지 않아 제공자 기본 모델로 실행합니다.
- **모델을 바꾸면 튜터 스레드는 다음 턴에 재구성합니다**(ai-system.md 스레드 매핑 전략). 실행기가 저장된 `providerModel`과 이번 모델을 비교합니다.
- **추론 강도는 작업 정의 값을 쓰고, 모델이 지원하지 않으면 가장 가까운 낮은 값으로(없으면 높은 값으로) 옮깁니다**(ai-system.md 모델 선택). 지원 목록을 모르면 그대로 둡니다. 설계 와이어프레임의 "추론 강도" 선택 상자와 `ai.reasoningEffort` 설정은 이번 범위가 아닙니다(작업별 기본값이 학습 흐름에 맞게 정해져 있어 학습자가 바꿀 근거가 아직 없음).
- 화면은 선택 상자 대신 라디오 그룹입니다. 설계가 요구하는 모델 설명과 지원 추론 강도를 각 선택지 아래에 보여 줄 수 있고, 모델 수가 몇 개뿐이라 한눈에 비교하는 편이 낫습니다. 상세: [AI 시스템 설계 구현 메모 (v1.0)](/docs/design/ai-system.md#구현-메모-v10), [UI/UX 설정](/docs/design/ui-ux.md#설정).

## D-061. "최근 활동"과 개념 상세의 "관련 문제"는 기존 기록에서 파생 — `확정`
- 2026-11-16, 사용자가 위임한 결정(M7 작업, FR-DASH-01·FR-DASH-02·FR-EX-10, P0 점검 M7 6·7번). D-037이 "학습 세션 기록이 생길 때까지" 미룬 카드입니다.
- **학습 세션 테이블(`study_sessions`)을 만들지 않고 연습 세트를 "세션"으로 씁니다.** ui-ux.md는 "최근 5개 세션 요약"이고 예시 행은 "화살표 함수 연습 7문제 · 정답 5", "복습 6개 개념 · 숙련 상승 2", "반복문 단원 완료"입니다. 이 문장들은 모두 연습 세트(`practice_sets`, 항목, 마지막 시도, `mastery_evidence`의 단계 상승)와 `lesson_progress.completed_at`으로 만들 수 있습니다. 세션 경계(유휴 시간으로 끊기)를 새로 기록하면 마이그레이션, 복원·초기화·평가 종료와 맞출 상태, 하트비트와의 중복이 생기고, 그 경계가 학습자에게 더 의미 있는 단위라는 근거가 없습니다. 단원별 실제 소요 시간 기록(M7 8번, 병렬 작업)과도 겹치지 않습니다.
- **행은 연습 세트마다 하나**(답한 문항이 하나 이상인 세트, 마지막 활동 순)이고, 통과한 단원 세트는 그 단원의 완료를 같은 행에 "단원 완료"로 붙입니다. 세트 행이 없는 단원 완료(프로젝트 단원)는 따로 "… 단원 완료" 행이 됩니다. 기본 5개, `GET /activity/recent?limit=`(최대 20). 시각은 학습자 하루 경계로 계산한 날짜로 "오늘 14:20 · 어제 14:20 · 11/11"을 정합니다. 와이어프레임의 "전체 보기 →"는 보여 줄 전체 기록 화면이 없어 뺐습니다.
- **진행 중인 단원 평가는 답한 문항 수만 보입니다**: 정답 수, 숙련 상승, 통과 여부는 평가가 끝날 때까지 `null`(learning-engine.md 단원 평가 세트, D-044와 같은 규칙).
- **"관련 문제"는 `GET /concepts/:id/exercises` 한 번으로** 그 개념이 주 개념인 연습 문제(`usage: practice`)를 쉬운 순서로, 문제마다 FR-EX-10 통계(`exerciseStats`를 한 번에 계산)와 함께 줍니다. `GET /exercises/:id/stats`를 문제마다 부르면 개념당 수십 번 요청이 되고, 개념 상세(`GET /concepts/:id`)에 넣으면 근거 "전체 보기"처럼 개념 상세를 다시 받을 때마다 통계까지 다시 계산합니다. 화면은 개념 상세를 먼저 보여 주고 목록은 따로 불러옵니다.
- **누설 규칙**: 평가·진단·프로젝트 문제는 목록에 넣지 않습니다(평가 문항을 미리 보여 주면 "처음 보는 문제"라는 평가 전제가 깨짐). 진행 중인 평가에 담긴 문제는 빼고, 통계도 그 평가의 시도를 세지 않습니다(D-051). 정답 키는 보내지 않고 지문만 보냅니다(이미 연습 세트에서 보이는 내용).
- 대시보드 배치는 와이어프레임대로 과정 진도(5열) 옆에 최근 활동(7열)이고, 약점 개념 카드는 아래 한 줄 전체로 옮겼습니다.

## D-062. 단원별 실제 학습 시간과 페이스 보정 — `확정`
- 2026-11-16, 사용자가 위임한 결정(M7, P0 점검 M7 항목 8, FR-GOAL-02). D-033의 "페이스 보정은 보류"를 이 결정으로 풉니다.
- **실제 시간은 하트비트로 셉니다.** 웹은 하트비트에 화면의 단원(`/learn/:lessonId`, 읽기·실습·프로젝트 모드 모두)을 `lessonId`로 실어 보내고, 서버는 그 하트비트가 센 활동 시간(2분 무입력·90초 간격·숨김 제외, 학습 시간과 같은 규칙)을 그날 학습 시간과 함께 `lesson_progress.active_ms`에 더합니다. 시도의 `active_ms`를 합하는 안은 버렸습니다: 읽기 시간이 빠지고, 시도 사이의 생각하는 시간도 빠집니다. `study_sessions` 테이블은 이번에도 만들지 않습니다(세션 경계가 필요한 기능이 아직 없음).
- **진행 중인 단원에만 더합니다**(`reading`·`practicing`). 완료한 단원을 다시 보는 시간은 "그 단원을 끝내는 데 걸린 시간"이 아니므로 보정을 왜곡합니다. 학습자가 연 적 없는 단원(행 없음)에는 행을 만들지 않습니다. 화면을 옮긴 직후 하트비트 하나(최대 30초)는 새 단원에 붙을 수 있습니다.
- **마이그레이션 전 단원은 "모름"(NULL)입니다.** `0006`은 `active_ms`를 기본값 없는 열로 더해 기존 행을 NULL로 두고, 새로 시작한 단원만 0부터 셉니다. 이미 진행 중이던 단원에 남은 시간만 더하면 실제보다 짧게 잡혀 보정이 빨라 보이기 때문입니다. `upsertLessonProgress`는 이 열을 쓰지 않고(새 행만 0), 하트비트만 원자적 `UPDATE … + ?`로 더합니다.
- **보정은 설계 그대로**: 완료 단원(`kind: lesson`만, 과정 무관) 5개 이상에서 실제/예상 비율의 중앙값, 0.5~2.0으로 제한(`paceCalibration`). 과정을 가리지 않는 이유는 학습자의 속도를 재는 것이고, 목표 과정 단원만 보면 새 과정을 시작할 때마다 보정이 사라지기 때문입니다. 평가·프로젝트는 페이스에 넣지 않으므로 보정 근거에서도 뺍니다.
- **오늘의 학습도 같은 비율을 씁니다.** 이어서 학습·새 단원 블록과 "시간이 남으면"의 남은 시간, `continue_lesson` 이유의 분 수가 모두 보정되고, 목표 과정이 없어도 보정합니다(`DailyPlanInput.calibration`). 페이스에만 보정을 쓰면 같은 단원이 페이스 화면과 오늘의 학습에서 다른 시간으로 보입니다.
- 상세: [학습 엔진 설계 구현 메모 (v1.0)](/docs/design/learning-engine.md#구현-메모-v10), [데이터 모델 lesson_progress](/docs/design/data-model.md#lesson_progress).

## D-063. 코드 초안의 서버 보관과 복원 규칙 — `확정`
- 2026-11-16, 사용자가 위임한 결정(M7, P0 점검 M7 항목 9, FR-CODE-06, NFR-04).
- **문제 단위 한 행, 제출 뒤에도 유지**(data-model.md 보관 정책). `code_drafts`의 키는 `(learner_id, kind, ref_id)`이고 `kind`는 `exercise`(코드 문제: `implement_function`·`fix_bug`·`web_task`, 프로젝트 포함)와 `example`(레슨의 수정 가능한 `<RunnableExample>`, `ref_id = <lessonId>#<exampleId>`)입니다. 설계 표의 `exercise_id` 대신 두 종류를 담고, `practice_set_item_id`를 더하고, `client_rev`는 두지 않습니다(아래 `updated_at`이 같은 일을 함). API: `GET·PUT·DELETE /code-drafts/exercises/:id`, `GET /lessons/:id/example-drafts`, `PUT·DELETE /lessons/:id/example-drafts/:exampleId`.
- **저장 경로**: 편집할 때마다 브라우저(localStorage)에 즉시, 서버에는 마지막 편집 2초 뒤(디바운스), 탭을 숨기거나 화면을 떠날 때 한 번 더(`keepalive`) 보냅니다. 설계의 IndexedDB 대신 localStorage를 그대로 씁니다: 동기 API라 입력 직후 바로 저장되고, 초안은 문제당 수 KB라 용량 문제가 없습니다. 상태 문구는 "저장됨 · 이 브라우저"(서버 전송 전·실패) → "저장됨"(서버 저장)입니다.
- **복원은 더 최근 편집이 이깁니다**(system-architecture.md "충돌 시 최신 수정 시각"). `updated_at`은 서버 수신 시각이 아니라 브라우저의 편집 시각이고, 서버는 저장된 것보다 오래된 쓰기(늦게 도착한 요청, 다른 탭)를 무시합니다(`applied: false`). 로컬 앱이라 브라우저와 서버의 시계가 같습니다. 서버 초안을 받지 못해도 화면은 열리고 브라우저 초안이나 시작 코드로 시작합니다. v0.3의 세트 항목 단위 브라우저 초안은 가장 오래된 초안으로 한 번 읽습니다.
- **연습 세트 항목에서 쓴 초안은 그 항목에만 복원합니다.** 같은 문제가 나중에 복습·약점·다시 풀기 세트에 나오면 시작 코드에서 시작합니다. 이전 답을 채워 두면 인출 연습이 되지 않고, 복습 세트에서는 정답을 보여 주는 것과 같기 때문입니다. 초안 행은 그대로 두었다가 새 항목에서 편집하면 덮어씁니다. 프로젝트와 레슨 예제는 항목이 없어 항상 복원합니다.
- **프로젝트 이어 하기**는 더 최근 초안(브라우저·서버) → 마지막 제출 → 시작 코드이고, 초안이 마지막 제출과 같으면 "마지막으로 채점한 코드에서 이어서 해요"로 안내합니다. 채점 뒤에도 초안을 지우지 않습니다(D-049의 "채점에 성공하면 초안을 지움"을 바꿈).
- **레슨 예제는 "코드 수정"으로 편집을 엽니다**(설계의 `editable` 기본 true를 이번에 구현). 처음부터 편집기를 띄우지 않는 것은 레슨 본문이 읽기 화면이고 예제마다 편집기를 만들면 무겁기 때문입니다(ui-ux.md "화면에 들어올 때 지연 생성"). 수정한 코드가 있으면 다시 열 때 편집기로 보여 주고, "원래 코드로"는 브라우저·서버 초안을 모두 지웁니다. CSS만 있는 예제와 `editable={false}` 예제는 편집할 수 없고 서버도 초안을 거절합니다.
- **코드는 신뢰하지 않는 입력입니다.** 서버는 초안을 실행·해석하지 않고 문자열로만 저장·반환합니다. 본문 320KB 제한, 파일 1~20개, 파일당 200,000자, 합계 256KiB(UTF-8), 경로는 실행 파일 경로 규칙(`..`·절대 경로 불가), 중복 경로·알 수 없는 키 거절. 코드 문제가 아닌 문제와 없는 예제는 거절해 임의 키로 행이 쌓이지 않게 합니다.
- **초기화·백업**: 초안은 학습 기록이므로 D-045 제외 목록 방식대로 초기화에서 지워집니다(별도 처리 없음). 백업은 user.db 전체라 그대로 들어갑니다. 복원·초기화가 끝나면 웹이 브라우저 초안을 모두 지웁니다: 브라우저 초안이 더 최근이라 복원한 서버 초안을 이기기 때문입니다.
- 상세: [데이터 모델 code_drafts](/docs/design/data-model.md#code_drafts), [UI/UX 설계 프로젝트 화면](/docs/design/ui-ux.md#프로젝트-화면).

## D-064. M7 성능·호환성 점검 방식과 CI 예산 — `확정`
- 2026-11-16, 사용자가 위임한 결정(M7 작업 5~7, P0 점검의 NFR-01·02·10 항목).
- **성능은 `pnpm perf`로 재현 가능하게 측정합니다.** 프로덕션 빌드, 실제 콘텐츠 팩, 임시 데이터 위치의 새 학습자로 Playwright Chromium에서 잽니다. 측정 구간은 페이지 안(입력 이벤트 또는 내비게이션 시작 → 기대한 요소가 있는 첫 애니메이션 프레임)이라 Playwright 왕복이 섞이지 않습니다. 항목마다 5회 재고 중앙값을 PRD 목표와 비교해, 넘으면 실패합니다. NFR-03은 수치가 없어 "무한 루프 중 가장 긴 프레임 간격 100ms 이하"(RAIL 응답 기준)로 봅니다. 결과: [성능 점검](/docs/reviews/2026-11-16-m7-performance.md).
- **CI에는 시간 기준을 넣지 않고 첫 화면 번들 크기 예산만 넣습니다(`pnpm check:bundle`).** 같은 기계에서도 1배 측정값이 ±50% 흔들렸고, CI runner(GitHub 호스트 또는 소유자 Mac, D-055)는 부하가 일정하지 않아 여유를 크게 둔 시간 기준도 가끔 실패하거나, 실패하지 않을 만큼 느슨하면 회귀를 잡지 못합니다. 첫 화면 회귀의 흔한 원인은 무거운 라이브러리가 첫 로드에 들어오는 것이고, 이는 gzip 바이트 수로 결정론적으로 잡힙니다. 예산은 현재보다 15~25% 높게(JS 220KiB, CSS 45KiB) 두고, 올릴 때는 PR에 이유를 씁니다. `pnpm perf`는 릴리스 전 확인 목록에 넣습니다([릴리스 절차](/docs/guides/release.md)).
- **이번에는 성능 수정을 하지 않습니다.** 1배 기준 모든 목표를 5배 이상 여유로 만족합니다. CPU 4배 감속에서 여유가 적은 학습 화면 첫 진입(1MB 조각)과 페이지의 첫 코드 실행은 개선 후보로 점검 기록에 남깁니다.
- **호환성은 E2E 설정의 opt-in 프로젝트로 점검합니다(`PW_COMPAT=firefox|webkit`, `pnpm test:e2e:compat`).** M1-B PoC처럼 Firefox는 출시판과 같게 사이트 격리(Fission)를 켜고 실행합니다. 범위는 샌드박스 정책 계열(`sandbox`, `sandbox-grading`)과 핵심 흐름(`flows`, `reading`, `practice`)입니다. 흐름 테스트가 공유 학습자를 바꾸므로 브라우저마다 서버를 새로 띄워 한 브라우저씩 실행합니다. 기본 E2E·CI 구성은 바꾸지 않습니다. 결과와 판단: [호환성 점검](/docs/reviews/2026-11-16-m7-compatibility.md).
- **Firefox·WebKit 실행은 아직 CI에 넣지 않고 릴리스 전 점검으로 돌립니다.** 샌드박스 설계는 CI에서 다른 엔진의 정책 계열을 돌리는 것을 목표로 했지만, 지금 CI는 소유자 Mac의 Docker에서 돌고(D-055) 실행마다 서버 네 개를 두 번 더 띄우면 e2e 작업이 5분 이상 길어집니다. Linux 이미지의 Firefox·WebKit 결과도 아직 확인하지 않았습니다. GitHub 호스트 runner로 돌아간 뒤 Linux에서 한 번 돌려 안정적이면 별도 작업으로 추가합니다.
- **다른 엔진의 차이는 Chromium 단언을 바꾸지 않고 `browserName` 분기로만 허용합니다.** 오류 문구·열은 Chromium에서만 검사하고(`forEngine`), 보안 판정(서버에 닿은 요청, 창·저장소 접근)은 모든 엔진에서 같게 검사합니다. Playwright가 Fission의 프로세스 밖 iframe을 다루지 못해 생기는 실패는 해당 확인만 건너뛰고 이유(`FISSION_FRAMES`)를 남깁니다. WebKit의 S48은 설계에 적힌 제약이라 건너뜁니다.
- **설치된 앱 스모크 테스트(`e2e/smoke`, `SMOKE_URL`)를 둡니다.** 릴리스 산출물을 임시 폴더에 설치해 실제 콘텐츠로 핵심 흐름을 확인하는 절차를 [릴리스 절차](/docs/guides/release.md#릴리스-산출물-확인)에 넣었습니다.

## D-067. 학습 화면 패널 조절·기억과 단축키 정리 — `확정`
- 2026-11-16, 사용자가 위임한 결정(M7, P0 점검 M7 항목 4·14, FR-UI-01·FR-UI-02).
- **패널 상태는 브라우저 `localStorage`에 둡니다(`proginone:panel:*`).** ui-ux.md 패널 규칙과 이미 있는 튜터 드로어 폭(`proginone:tutor-width`)과 같은 방식입니다. 패널 크기와 접힘은 화면 크기와 기기에 따라 달라지는 보기 취향이라 학습 기록이 아니고, 서버 설정(`settings`)에 두면 다른 크기의 창에서 같은 값을 강요하며 백업·초기화의 대상이 됩니다. 저장소를 쓸 수 없으면 기억만 하지 않습니다.
- **조절할 수 있는 것**: 실습 모드 문제 패널 | 작업 패널 비율(1280px 이상에서만, 문제 유형별, 최소 320px·기본 40%(`web_task`·프로젝트 28%)·최대 55%), 코드 작업 영역의 에디터 높이(240~900px, 처음에는 내용 높이)와 결과(테스트·콘솔) 접기, 읽기 모드 오른쪽 보조 열("이 단원의 개념"·목차) 접기, 튜터 드로어 열림. 핸들은 모두 공통 `PanelSeparator`(`packages/ui`, `role="separator"`·값·방향, `←→`/`↑↓` 10px, `Home`/`End`, 더블클릭 기본값, 포인터 드래그)이고 드래그 없이 키보드로 모두 조절됩니다(WCAG 2.5.7).
- **에디터/결과 분할은 비율 대신 에디터 높이(px)입니다.** 설계 표는 고정 높이 작업 패널을 가정해 "에디터 65%, 결과 최소 120px"이지만, 지금 실습 화면은 페이지 전체가 스크롤되고 작업 패널 높이가 정해져 있지 않아 비율의 기준이 없습니다. 학습자가 핸들을 움직이기 전에는 지금처럼 내용 높이를 쓰고, 결과를 접으면 핸들을 숨깁니다. 코드를 실행하거나 콘솔 오류 위치로 이동하면 접힌 결과를 다시 엽니다(실행 결과를 숨긴 채 두지 않음).
- **튜터 드로어 열림은 1280px 이상에서만 복원하고, 복원할 때는 포커스를 옮기지 않습니다.** 그보다 좁으면 드로어가 본문을 덮는 오버레이라 저절로 열리면 방해가 되고, 페이지를 열 때 포커스는 제목에 있어야 합니다(포커스 관리 규칙). 진행 중인 단원 평가에는 튜터가 없으므로 열리지 않습니다.
- **커리큘럼 레일은 이번에 만들지 않습니다.** 레일(접힌 56px·펼친 280px, `[` 토글)은 학습 화면에 아직 없고, 단원 이동은 과정 상세와 본문 아래 이전·다음 링크로 합니다. 레일 자체가 새 화면 요소라 패널 조절 범위를 넘으므로 후속 과제로 남기고, 단축키 도움말에도 넣지 않습니다.
- **실행 단축키: 문제는 `⌘'` 실행·`⌘Enter` 제출, 레슨 예제는 `⌘Enter` 실행입니다.** PRD는 "실행/제출(⌘Enter)", ui-ux.md는 문제의 실행을 `⌘'`로 정했습니다. 문제에서 `⌘Enter`를 실행에 쓰면 "확실해요" 제출과 겹치므로 ui-ux.md를 따르고, 제출이 없는 레슨 예제에서는 와이어프레임대로 `⌘Enter`가 실행입니다. 예제 단축키는 포커스가 그 예제(편집기·예측 입력란·버튼) 안에 있을 때만 동작해 한 페이지의 여러 예제가 함께 실행되지 않습니다.
- **평가 중 잠금은 단축키에도 적용합니다.** 진행 중인 단원 평가에서 `⌘J`·`⌘.`는 아무것도 열지 않고, 키를 가로채(Chrome의 `Ctrl+J` 다운로드 창 방지) "단원 평가 중에는 튜터와 힌트를 쓸 수 없어요. 평가가 끝나면 열려요." 토스트로 이유를 알립니다. 수정자 키가 있는 단축키는 CodeMirror 포커스 중에도 동작합니다(에디터가 이 키들을 묶지 않음).
- **단축키 도움말은 실제로 있는 단축키만 보여 줍니다.** 입력 중이 아닐 때 `?` 또는 학습 헤더의 키보드 버튼(1024px 이상)으로 엽니다. `⌘K`(P1), `G` 다음 `D`, `[`, `Alt+↑↓` 단원 이동, `⌘→`처럼 아직 없는 단축키는 구현할 때 목록에 넣습니다. 단일 문자 단축키 `?`는 입력란·에디터 포커스 중에 꺼지며, 설정에서 끄는 옵션(WCAG 2.1.4)은 단일 문자 단축키가 늘어날 때 둡니다.

## D-068. AI 오프라인과 로그인 만료 표시 — `확정`
- 2026-11-16, 사용자가 위임한 결정(M7, P0 점검 M7 항목 15, FR-UI-03, AI 완료 기준 "오프라인·인증 만료 오류 UI").
- **로그인 만료는 `logged_out` 상태의 `expired: true`로 구분합니다.** 새 상태(`expired`)를 더하면 서버 사전 검사·설정·튜터가 모두 새 분기를 가져야 하지만, 실제로는 "로그인이 없다"는 같은 상태이고 문구와 다음 행동만 다릅니다. Codex 어댑터는 턴이 `unauthorized`로 실패하거나, 계정이 있던 상태(`ready`·`rate_limited`)에서 앱이 요청하지 않은 계정 손실을 `account/read`로 확인하면 `expired: true`로 바꿉니다. 학습자가 "연결 해제"를 눌러 생긴 로그아웃과 계정 없이 처음 시작한 경우는 그대로 "연결 안 됨"입니다. 만료 상태의 AI 요청은 `AI_UNAUTHORIZED`(409)로 거절해 "AI 로그인이 만료되었습니다"를 보여 줍니다. 모의 제공자는 `[mock:error:AI_UNAUTHORIZED]` 질문에서 같은 상태로 바뀝니다(E2E).
- **문구와 다음 행동**: 헤더 "AI 로그인 만료"(amber), 튜터 드로어 제목 "ChatGPT 로그인이 만료됐어요"와 "다시 로그인하면 이어서 쓸 수 있어요. 학습 기록과 튜터 대화는 그대로 남아 있어요.", 드로어 안의 **다시 로그인** 버튼(ai-system.md "튜터 영역에 다시 로그인 버튼", 설정 화면과 같은 로그인 대화상자), 설정 > AI 제목 "ChatGPT 로그인이 만료됐어요"와 **다시 로그인**.
- **오프라인은 브라우저의 `navigator.onLine === false`만 믿습니다.** `false`는 네트워크가 전혀 없다는 뜻이라 AI(Codex → OpenAI)를 쓸 수 없는 것이 확실하지만, `true`는 제공자에 닿는다는 보장이 아니므로 그때는 제공자 오류가 말하게 둡니다. 앱 자체는 로컬 서버라 오프라인에서도 동작하므로(NFR-09) AI 진입점만 끕니다: 헤더 "AI 오프라인", 튜터 입력란과 AI 힌트·오답 설명 버튼 비활성 + 이유 "인터넷에 연결되어 있지 않아 AI를 쓸 수 없어요", 드로어 빈 상태 "인터넷에 연결되어 있지 않아요"(레슨·풀이·채점·복습은 그대로 된다는 안내), 설정 > AI 상단 안내. `online` 이벤트가 오면 저절로 다시 켜집니다. Codex 미설치·지원하지 않는 버전·격리 실패는 오프라인보다 그 문제를 먼저 보여 줍니다(인터넷이 돌아와도 풀리지 않음).
- 대시보드에는 AI 요소가 없어 전역 헤더의 AI 상태 표시가 같은 문구를 보여 줍니다.

- **판정은 단원 경고와 같습니다(D-052)**: 단원이 소개하는 개념의 직계 `required` 선수 개념 중 유효 숙련도 60 미만 또는 `practicing` 미만인 것. 과정 상세와 단원 화면이 서로 다른 말을 하지 않게 하려고 기준을 따로 두지 않습니다.
- **과정을 시작하기 전에는 아이콘을 하나도 보이지 않습니다.** 과정 안 단원(평가·프로젝트 포함) 중 진도 상태가 `not_started`가 아닌 것이 하나라도 있어야 표시합니다. 새 학습자에게는 첫 단원을 뺀 모든 단원의 선수 개념이 "아직 배우지 않음"이라 46개 행 대부분에 `!`가 붙고, 그러면 아이콘이 아무 정보도 주지 않습니다. 시작 전에는 요약 카드의 "학습 시작"이 올바른 안내입니다.
- **완료한 단원에는 표시하지 않습니다.** 이미 마친 단원에 "먼저 …부터"는 쓸모가 없고, 단원 화면을 다시 열면 D-052 경고는 그대로 보입니다. 평가·프로젝트 단원은 새 개념을 소개하지 않아 대상이 아닙니다(D-052와 같음).
- **API는 `GET /courses/:id/prerequisite-warnings`로 나눕니다.** `GET /courses/:id`는 content.db만 담아 웹이 `staleTime: Infinity`로 캐시하므로 숙련도를 섞지 않습니다(D-052의 `GET /lessons/:id/prerequisites`와 같은 이유). 응답은 표시할 단원과 약한 개념(소개 단원 포함)만 담고, 실패하거나 받는 중에는 행에 아이콘이 없을 뿐 화면은 그대로입니다. 웹은 30초 동안 캐시합니다.
- **아이콘은 행 링크 옆의 별도 링크입니다.** 행 링크 안에 두면 중첩된 상호작용 요소가 되므로 `li` 안에서 행 링크와 나란히 둡니다. 접근 가능한 이름은 "선수 개념 안내: 먼저 ‘…’부터 확인하면 더 쉬워요. ‘…’ 단원 보기", 마우스 오버와 키보드 초점에서 같은 문장을 툴팁(Radix, Esc로 닫힘)으로 보입니다. 누르면 첫 약한 개념을 소개하는 단원으로(없으면 개념 상세로) 갑니다. 문구는 ui-ux.md의 "먼저 ‘형 변환’을 공부하면 더 쉬워요" 대신 단원 경고와 같은 "먼저 ‘…’부터 확인하면 더 쉬워요"를 씁니다. 개념 이름의 받침에 따라 조사가 바뀌는 문제를 피하고, 두 화면의 말을 맞춥니다.

## D-074. 학습 화면 코드 분할과 실행 준비, 미리보기 이동 안내, 엔진별 오류 설명 — `확정`
- 2026-11-16, 사용자가 위임한 결정(M7 후속 작업 5·8·9, [성능 점검](/docs/reviews/2026-11-16-m7-performance.md)과 [호환성 점검](/docs/reviews/2026-11-16-m7-compatibility.md)의 개선 후보).
- **러너의 준비 단계(`packages/runner/src/prepare`, parse5·acorn)를 동적 `import()`로 나눕니다.** 학습 화면 조각이 1,015KB(gzip 330KB)에서 724KB(gzip 246KB)로 줄고, 준비 단계는 별도 조각(291KB, gzip 83KB)이 됩니다. `@proginone/runner` 진입점은 더 이상 준비 단계를 다시 내보내지 않고(`export *`가 있으면 번들러가 정적 의존으로 보고 나누지 못함), 필요한 곳은 `@proginone/runner/prepare`를 씁니다. 호스트의 `run()`은 준비 단계를 받는 동안 셸 연결을 함께 시작합니다.
- **코드를 실행할 수 있는 화면(실습 문제, 프로젝트, 레슨 예제)이 뜨면 유휴 시간에 실행 환경을 미리 준비합니다**(`warmRunner`: 준비 단계 받기 + 공유 숨김 셸 연결). 셸은 앱 전체에서 하나를 재사용하므로 비용은 세션당 한 번입니다. `requestIdleCallback`이 없는 브라우저(현재 Safari)와 jsdom은 건너뜁니다. 시간만 줄이는 최적화라 없어도 동작은 같습니다. 화면이 뜨자마자 만들지 않고 유휴 시간을 기다리는 이유는 첫 화면 그리기와 겹치지 않게 하려는 것입니다(제한 2초).
- **CodeMirror 지연 로드는 이번에 하지 않습니다.** 학습 화면 조각의 나머지 대부분(약 1MB 원본)이 CodeMirror인데, 읽기 모드의 레슨 예제도 편집기를 바로 보여 주므로 지연하면 자리 표시와 교체가 필요하고 시각 기준 이미지가 바뀝니다. 같은 시기에 학습 화면 레이아웃을 바꾸는 작업이 있어 겹침을 피했습니다. 후속 후보로 둡니다.
- **미리보기 문서가 가로챌 수 없는 이동(`location` 대입, `form.submit()`, `<meta refresh>`)을 하면 브라우저 오류 화면 대신 안내 문서로 바꿉니다.** 하네스가 `preview` 모드에서 `pagehide` 때 셸에 `pg-left`를 보내고, 셸은 그 미리보기 iframe의 `srcdoc`을 스크립트 없는 정적 안내("미리보기는 다른 페이지로 이동할 수 없어요. … 코드를 다시 실행하면 처음 화면으로 돌아와요.")로 바꾸며 기존 `navigation-blocked` 알림도 보냅니다. 떠나는 문서가 보낸 메시지는 브라우저가 버릴 수 있어(Chromium E2E에서 확인), 셸은 하네스 인사 뒤 미리보기 iframe의 두 번째 `load`도 이동으로 봅니다. 학습자 코드도 `pg-left`를 보낼 수 있지만 자기 미리보기를 안내 문서로 바꿀 뿐입니다. 샌드박스 플래그·CSP는 그대로입니다. 링크 클릭·폼 제출은 기존처럼 하네스가 시작 전에 취소합니다(#73). 호환성 점검에서 Firefox·WebKit의 막힌 `location` 이동은 `pagehide` 없이 시간 초과로 끝났으므로, 그 엔진들에서는 문서가 그대로 남고 안내 문서로 바뀌지 않습니다.
- **콘솔의 학습자 언어 설명은 V8·SpiderMonkey·JavaScriptCore 문구를 모두 알아봅니다.** 원래 오류 문구는 엔진 그대로 보여 주고(D-030), 아래 설명만 엔진별 문구 대응표(`ENGINE_MESSAGES`)로 고릅니다: 선언되지 않은 이름(`is not defined`, `Can't find variable:`, `assignment to undeclared variable`), 초기화 전 접근(새로 추가), `undefined`/`null` 속성 접근, `const` 재할당, 무한 재귀(`Maximum call stack size exceeded`, Firefox의 `InternalError: too much recursion`, 새로 추가). 호환성 점검 개선 후보 1·3입니다. 후보 2(Firefox·WebKit에서 막힌 `location` 이동이 시간 초과로 끝나는 것)는 엔진별로 이동 시도를 감지할 방법을 확인해야 해 후속으로 둡니다.

## D-077. 단계형 레슨 읽기 — `확정`
- 2026-11-17, 학습자(사용자) 결정(시안 B)과 그 위임 범위의 구현 결정. 학습자 의견: "강의 글이 구분 없이 md 읽는 느낌이라 눈에 안 들어온다".
- **콘텐츠는 그대로 두고 화면에서 표준 섹션을 다섯 단계로 묶습니다.** 1 "왜 배울까"(objectives, prerequisites, intro) · 2 "원리"(principle) · 3 "직접 해 보기"(examples, walkthrough) · 4 "주의"(pitfalls, in-practice) · 5 "확인"(check, practice, summary, next). 제안된 묶음 그대로입니다. 단계마다 흰 카드, 종류 칩(색 다름), 큰 섹션 제목(28px)을 두고, 위에 밝은 초록 히어로 띠(과정·모듈, 제목, 한 줄 소개, 읽기·전체 시간, 연습 문제 수), 헤더에 "단계 n / 전체"와 진행 막대, 왼쪽에 세로 진행선을 둡니다. 단원 평가·프로젝트 단원은 지금처럼 흰 카드 하나에 흐릅니다.
- **묶기 규칙**: 섹션이 없는 단계는 빼고 셉니다. 순서는 절대 바꾸지 않습니다: 표준 순서보다 앞 단계의 섹션이 뒤에 오거나 표준이 아닌 섹션이 있으면 지금 단계에 남깁니다. 표준 섹션이 하나도 없으면 단계 없이 보여 줍니다. 섹션 제목은 그대로 `h2`이고 단계는 `role="group"`("n단계: 종류")이라 제목 구조와 기존 랜드마크가 바뀌지 않습니다.
- **잠그지 않습니다.** 남은 단계는 연한 배경·그림자 없음·회색 칩으로 조용하게만 보이고, 글자 투명도는 낮추지 않습니다(시안의 `opacity: .55`는 본문 대비를 AA 아래로 떨어뜨림). 시안의 "앞 단계를 마치면 열려요"는 쓰지 않습니다. 학습자가 원하는 곳을 먼저 읽을 수 있어야 하고(D-011 "다 읽지 않아도 연습으로"), 스크롤만으로도 진행을 인식합니다.
- **현재 단계**는 스크롤 위치(카드 위쪽이 화면 35% 선을 지난 마지막 단계, 페이지 끝에서는 화면 안의 마지막 카드)와 "다음 단계" 버튼으로 바뀝니다. 버튼은 다음 카드로 스크롤(reduced-motion이면 즉시)하고 그 카드에 포커스를 옮기며, 스크롤 중 1초 동안은 스크롤 판정을 쉽니다. 처음 구현한 IntersectionObserver(35% 띠) 방식은 페이지 맨 위에서 첫 카드가 띠보다 아래에 있어 1단계로 돌아오지 못해, 스크롤 이벤트에서 카드 위치를 직접 재는 방식으로 바꿨습니다.
- **단계 기억은 기존 읽기 진도의 `lastSectionId`로 합니다**(새 API·마이그레이션 없음). 저장하는 섹션은 현재 단계를 따라갑니다: 화면의 섹션이 현재 단계에 속하지 않으면 그 단계의 첫 섹션을 저장합니다. 다시 열면 그 섹션의 단계로 즉시 이동합니다. 이미 스크롤했거나 URL에 `#…`가 있으면 이동하지 않고, "지난번에 n단계 ‘…’의 ‘…’까지 읽었어요. 이어서 읽기" 안내를 남깁니다.
- **히어로의 연습 문제 수**를 위해 `GET /lessons/:id`에 선택 필드 `practiceCount`(그 단원의 `usage: practice` 문제 수)를 더했습니다. 없으면 타일을 숨깁니다.
- **본문 타이포그래피를 키웠습니다.** 본문 18px/1.8(설정 작게 17·보통 18·크게 20px, 이전 16·17·19px), 본문 색 `--color-text-prose`(`#33453b`), 섹션 제목 28px/800(카드의 첫 섹션)·22px/700(이어지는 섹션). Callout·Pitfall(잘못된 생각·실제 동작·올바른 이해를 나란히)·CompareTable·InlineExercise·학습 목표("목표 n" 상자)를 카드 안 연한 배경 상자로 다듬었습니다. 한 줄로 쓴 `<Wrong>`·`<Actual>`·`<Right>`가 문단에 싸여 오던 것(블록이 `<p>` 안에 들어감)도 이때 풀었습니다.
- **레슨 코드는 테마와 관계없이 어둡습니다**(`#10231a`, 시안 B). D-024의 "레슨 코드 블록과 실습 에디터가 같은 모습" 근거를 레슨 쪽에서는 바꿉니다: 학습자가 고른 시안이 어두운 코드 상자이고, 카드 안에서 코드가 본문과 뚜렷이 구분됩니다. 실습 화면의 에디터는 D-024대로 라이트 기본, "작업대 어둡게" 설정도 그대로입니다. 코드 토큰은 `light-dark()` 폴리필 때문에 `:root`에서 값이 정해지므로, 레슨 코드 영역에서 다크 값을 직접 다시 지정합니다(`.workbench`와 같은 방식).

## D-078. 기본 테마는 라이트, 헤더에서 라이트·다크 전환 — `확정`
- 2026-11-17, 학습자(사용자) 결정과 그 위임 범위의 구현 결정. 학습자 요구: "기본 테마를 light 테마로 바꾸고, 상단에서 테마 바꿀 수 있도록 하자."
- **기본값 `theme`을 `system`에서 `light`로 바꿉니다.** 설정에 테마를 저장한 적 없는 학습자(새 설치, 그리고 지금까지 기본값을 쓰던 학습자)는 운영체제가 다크여도 라이트로 봅니다. D-076의 밝은 초록 색 체계가 라이트를 기준으로 다듬어졌고, 학습자가 그 모습을 기본으로 원했습니다. 설정 > 화면의 "시스템"(운영체제 따름)은 그대로 고를 수 있고, 이미 저장한 `system`·`dark`는 바뀌지 않습니다. 설정은 저장한 키만 행으로 남기므로 마이그레이션은 없습니다.
- **헤더의 아이콘 버튼으로 라이트 ↔ 다크를 바꿉니다.** 전역 헤더와 학습 헤더 오른쪽에 두고, 누르면 지금 보이는 테마의 반대를 설정 `theme`에 저장합니다. `system`이면 운영체제가 지금 보여 주는 테마의 반대를 고릅니다(누른 뒤에는 명시 값이 되어 운영체제를 따르지 않음). 세 값을 돌아가며 고르는 안은 버렸습니다: 한 번 눌러 아무것도 안 바뀌는 단계(`system`)가 생기고, 운영체제 따름은 자주 바꾸는 설정이 아니라 설정 화면에 두면 충분합니다.
- **아이콘·이름은 다음 동작입니다.** 라이트일 때 달(`Moon`)과 "다크 테마로 바꾸기", 다크일 때 해(`Sun`)와 "라이트 테마로 바꾸기"를 접근 가능한 이름과 툴팁으로 씁니다. 상태("다크 모드 켜짐")를 말하는 토글 버튼(`aria-pressed`)은 `system`일 때 눌림 상태가 모호해서 쓰지 않았습니다.
- **즉시 반영하고 실패하면 되돌립니다.** 버튼은 설정 캐시를 먼저 바꿔(ThemeSync가 `<html>`에 적용) 저장 요청을 보내고, 실패하면 그 사이 다른 변경이 없을 때 이전 값으로 되돌린 뒤 "테마를 바꾸지 못했어요" 토스트를 띄웁니다. 설정을 받기 전에는 버튼이 비활성입니다.
- **1024px 미만의 전역 헤더에서는 메뉴 패널 마지막 줄**("다크 테마로 바꾸기" 등 글자와 아이콘)로 옮깁니다. 390px 헤더 한 줄에는 목표 칩, AI 상태, 설정, 메뉴 버튼이 이미 있어 자리를 아꼈습니다. 학습 헤더는 메뉴가 없어 버튼을 그대로 두고, 1024px 미만에서 간격을 12px에서 8px로 줄여 390px에 맞췄습니다. 단원 평가 중에도 쓸 수 있습니다(화면 모습만 바꾸고 평가에 영향이 없음).
- **첫 화면 깜빡임 방지 캐시를 바꿉니다.** 이전에는 `light`·`dark`만 `localStorage`(`proginone.theme`)에 두고 `system`이면 지웠습니다. 기본값이 라이트가 되면 "캐시 없음"을 라이트로 칠해야 하므로, `system`도 캐시에 저장하고 `theme-init.js`는 `dark` → 다크, `system` → 속성 없음(운영체제 따름), 그 밖(없음·`light`·알 수 없는 값·저장소 사용 불가) → 라이트로 칠합니다. 이전 버전에서 `system`을 저장해 둔 학습자는 캐시가 없으므로 업데이트 뒤 첫 로드에서 한 번 라이트로 그려졌다가 운영체제 테마로 바뀔 수 있고, 그 뒤로는 캐시가 맞습니다.
- E2E는 라이트·다크 화면을 `emulateMedia`로 고르므로, 주 서버와 첫 실행 여정 서버의 학습자를 시작할 때 `system`으로 둡니다(`e2e/tests/onboarded.setup.ts`). 같은 설정 단계에서 새 학습자가 다크 운영체제에서도 라이트로 시작하는지 확인합니다.
- 상세: [UI/UX 설계 전역 내비게이션](/docs/design/ui-ux.md#전역-내비게이션), [디자인 토큰 구현 메모](/docs/design/ui-ux.md#디자인-토큰).

## D-081. 단원 통과의 개념 조건은 세트 안 성과로 — `확정`

- 2026-11-17, 학습자 보고에 따른 조율자 결정. 학습자 보고: "연습을 마치고 통과 기준에 못 미쳐서 다시 연습했고 전부 맞췄는데 아직도 통과 기준에 못 미친다고 뜬다."
- 원인: 통과 규칙의 개념 조건 `minConceptScore`(50)가 장기 숙련도 `concept_mastery.score`를 썼습니다. 이 점수는 여러 세션과 복습 간격에 걸쳐 쌓이도록 설계되어(반복·저난이도 감쇠, 단계 게이트) 한 세트로는 잘 오르지 않습니다. `html.basics.how-web-works`에서는 두 번째 세트를 전부 맞혀도 `html.web.client-server`가 40.4였고, `html.basics.document` 첫 세트에서는 13문제 중 11문제(신용 정답률 0.954)를 맞혔는데 소개 개념 5개가 모두 50 미만(최고 34.4)이라 통과하지 못했습니다.
- **개념 조건을 세트 안 성과로 판정합니다(`minConceptCredit`, 기본 0.6).** 단원이 소개하는 개념마다, 이번 세트에서 그 개념이 주 개념(가중치 1)인 항목들의 신용 정답률(`o × W_hint × W_try` 평균, 건너뜀 0)이 0.6 이상이고 그중 1개 이상을 맞혀야 합니다(마지막 시도 `o ≥ 0.5`). 세트에 그 개념 항목이 없으면 판정에서 뺍니다(점수 조건으로 되돌리지 않음). 재학습 항목은 다른 기준과 같이 뺍니다.
  - 근거: 단원 완료는 "이번 단원 내용을 이해했는가"를 묻는 판정이고, 장기 점수는 "얼마나 오래 기억하고 연습했는가"를 나타냅니다. 장기 점수를 쓰면 몇 문제만 틀려도(또는 다 맞혀도) 막힙니다. 개념별 바닥선은 세트 전체 정답률이 높아도 한 개념을 통째로 놓친 경우를 잡습니다. 0.6은 2문항 중 1개만 맞히면(0.5) 미달, 3문항 중 2개면(0.67) 충족이 되는 값입니다.
  - 버린 대안: "세트에서 그 개념 문제를 모두 첫 시도에 맞히면 점수 조건 예외"(이 결정의 첫 안. 몇 문제만 틀려도 여전히 장기 점수에 막힘), 기준 점수 낮추기·감쇠 완화(점수의 의미가 바뀌고 복습·약점 판정에 영향).
- **`concept_mastery.score`는 그대로 개념 지도, 복습, 약점 판정, `mastered` 게이트에 씁니다.** 단원 완료 판정에만 쓰지 않습니다.
- **필드**: `PassRule.minConceptScore`를 `minConceptCredit`으로 바꿨습니다. `lesson.yaml`의 `practice.passRule.minConceptCredit`(0~1)으로 단원별로 덮어쓸 수 있습니다. 이미 저장된 세트의 `pass_rule_json.minConceptScore`는 호환용으로 읽기만 하고 무시하며, `minConceptCredit`이 없으면 엔진 기본값을 씁니다. `result_json`에는 개념별 `{conceptId, credit, correct, total, met}`과 미달 개념(`below`)을 담고, 이전 결과의 `minConceptScore`는 그대로 읽힙니다. 학습 엔진 `1.3.0`.
- **요약 화면**: 미달 개념마다 "‘요소’ 이번 연습 1/3 정답"과 다음 행동(한 번 더 연습, 약점 집중, 다음 단원으로 넘어가도 됨)을 같은 목록 항목에 두어 스크린 리더도 함께 읽습니다.
- **통과하지 못해도 "다음 단원"을 늘 보여 줍니다.** 설계는 처음부터 "통과하지 못해도 다음 단원을 막지 않는다"였지만, 요약 화면이 통과했을 때만 다음 단원 링크를 보여 줘 학습자는 막힌 것으로 느꼈습니다. 통과하지 못했을 때는 "한 번 더 연습"이 주 버튼, "다음 단원으로: (제목)"이 보조 버튼입니다. 다음 단원 진입을 실제로 막는 곳은 서버·화면 어디에도 없었습니다.
- **콘텐츠를 보강합니다.** HTML/CSS에서 주 개념 문제가 3개 이하이고 모두 난이도 2 이하인 개념이 19개였습니다. 작은 풀은 세트를 다시 해도 같은 문제가 반복됩니다. `html.web.client-server`에 난이도 2~3 문제 3개를 더하고, 같은 상황의 개념 중 단원 상한(HTML/CSS 6~12개)에 자리가 있는 단원의 개념 5개(`html.text.emphasis`, `html.content.paths`, `css.box.areas`, `css.units.length`, `css.type.font-properties`)에 2개씩, 모두 13개를 더했습니다(유형 구성비 ±10%p 안). 독립 AI 검토자가 전수 검토해 승인했습니다([검토 기록](/docs/reviews/2026-11-17-d081-htmlcss-concept-items-review.md)). 여섯 단원의 `practice.targetCount`를 새 승인 수에 맞췄습니다.
  - `html.basics.how-web-works`는 15개가 되어 상한 12를 넘고 `unit-count-over` 경고 1개가 남습니다. 이 단원의 개념 3개가 모두 작은 풀이라 기존 문제를 빼면 다른 개념이 같은 상황이 되므로 상한을 넘는 쪽을 택했습니다(상한 초과는 원래 경고만 내는 규칙). 단원이 이미 12개인 `document`·`forms`·`flex-basics`의 같은 상황 개념(`html.doc.*` 4개, `html.forms.inputs`·`labels`·`buttons`, `css.flex.container`·`axes`)과 `html.content.links`, `html.text.paragraphs`, `css.box.spacing`, `css.colors.notation`은 이번에 보강하지 않았습니다.
- 상세: [학습 엔진 설계 단원 연습 세트](/docs/design/learning-engine.md#단원-연습-세트), [구현 메모 (D-081)](/docs/design/learning-engine.md#구현-메모-d-081), [UI/UX 설계 단원 완료 순간](/docs/design/ui-ux.md#단원-완료-순간).

## D-083. 과정 목록·상세에 진도 표시 — `확정`

- 2026-11-17, 학습자(사용자) 요구와 그 위임 범위의 구현 결정. 학습자 요구: "과정 탭에서 커리큘럼의 각 항목이 완료되었는지, 얼마나 진행한 상태인지 등이 표시되면 좋겠다."
- **진도의 기준은 대시보드 "과정 진도"와 같습니다.** 완료한 단원 수 ÷ 전체 단원 수이고, 단원 평가·프로젝트 단원도 한 단원으로 셉니다. `GET /mastery`가 이미 이렇게 세고 있었고, 과정 화면과 대시보드가 다른 숫자를 보이면 학습자가 어느 쪽을 믿을지 헷갈립니다. 계산은 서버의 `countCompleted`(course-progress-service) 하나를 두 API가 같이 씁니다. 평가·프로젝트를 빼는 안은 버렸습니다: 모듈을 끝냈다는 표시가 평가 통과 전에 나오고, 대시보드 숫자도 함께 바꿔야 합니다.
- **과정 상태**는 시작 전(과정 안 모든 단원이 `not_started`), 진행 중, 완료(모든 단원 `completed`)입니다. 단원이 없는 과정은 시작 전입니다.
- **"지금 할 단원"**은 그 과정에서 `updated_at`이 가장 최근인 읽는 중·연습 중 단원이고, 없으면 과정 순서상 첫 미완료 단원입니다. 대시보드 "이어서 학습"(전체 과정에서 가장 최근의 읽는 중·연습 중 단원)과 같은 규칙을 과정 하나로 좁힌 것입니다. 첫 미완료 단원만 쓰는 안은 앞 단원을 건너뛰고 뒤 단원을 읽던 학습자를 엉뚱한 곳으로 보내서 버렸습니다. 과정을 시작하기 전에는 강조하지 않고 요약 카드의 "학습 시작"만 둡니다(D-073처럼 새 학습자 화면을 조용하게 둠).
- **API를 따로 둡니다**: `GET /course-progress`(과정 목록용 요약: 완료 수, 상태, 지금 할 단원)와 `GET /courses/:id/progress`(요약 + 모듈별 완료 수 + 단원별 상태·읽은 비율). `GET /courses`·`GET /courses/:id`는 content.db만 담아 웹이 `staleTime: Infinity`로 캐시하므로 학습자 데이터를 섞지 않습니다(D-052·D-073과 같은 이유). 목록 경로를 `GET /courses/progress`로 하지 않은 것은 커리큘럼 라우트의 `GET /courses/:id`가 먼저 등록되어 `progress`를 과정 id로 받기 때문입니다. 웹은 두 진도 질의를 마운트할 때마다 다시 받고(`staleTime: 0`, 단원 읽기는 웹의 변경 요청을 거치지 않음), 연습·프로젝트가 끝나면 다른 학습 상태와 함께 무효화합니다. 받는 중이거나 실패하면 진도 표시 없이 이전 화면 그대로입니다.
- **완료한 과정의 버튼은 "복습하기"이고 복습 화면(`/review`)으로 갑니다.** 과정을 다 마친 뒤에 할 일은 FSRS 복습이고, 첫 단원을 다시 여는 것보다 기억 유지에 맞습니다.
- **상태는 색만으로 구분하지 않습니다.** 단원 행 아이콘은 모양이 모두 다르고(원 체크·연필·채워지는 고리·빈 원), 상태 글자("완료", "연습 중", "읽는 중 45%", 시작 전은 스크린 리더 전용)를 행 링크 이름에 넣습니다. 지금 할 단원은 링크에 `aria-current="step"`을 둡니다. 과정 목록 카드의 "이어서 학습"은 카드 제목 링크(카드 전체를 덮는 `::after`)와 나란한 별도 링크라 링크가 중첩되지 않습니다.
- 색은 D-076 토큰만 씁니다. 대비 검사에 단원 번호/선택 배경, 진도 채움/선택 배경, 완료 아이콘/표면 쌍을 더했습니다.
- 기존 과정 목록·상세 기준 이미지(시각 회귀)는 새 학습자 상태로 진도 API를 고정해 다시 만들었고(시작 전 칩과 0% 막대가 생김), 진행 중 학습자 상태 두 장(과정 목록 라이트, 과정 상세 다크)을 더했습니다.
- 상세: [UI/UX 설계 과정 진도 표시](/docs/design/ui-ux.md#과정-진도-표시구현-d-083).
